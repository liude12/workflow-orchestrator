产品团队 AI 协作工作流使用手册

适用对象：产品经理、业务负责人、设计人员及参与评审的研发和测试人员。GitHub 手册版本 20261110.13，适用于已接入五项专业方法、支持 S4 UI/UX 资料按需补充的工作流版本。

使用这个 Skill 时，把产品想法、已有资料、项目位置和本次希望完成的工作交给 AI。AI 会按需要澄清需求、梳理业务、设计功能、制作原型并编写 PRD 和 SRS，同时维护文件与版本。你负责补充真实事实、决定重要业务取舍，并审核具体成果。

第一次使用，先读第 1—3 节；已有项目从第 7 节继续。每段示例指令中的 【内容】 都需要换成自己的信息。示例是对 AI 的自然语言请求，不是需要粘贴到 PowerShell 的命令。

HTML 版的示例可点击“复制指令”；若客户端限制剪贴板，点击“选中全文”后使用系统复制快捷键，也可以手动选择文字。

1 首次上手#

按下面的顺序完成一次实际操作，先熟悉入口和反馈方式。

  1. 获取整个仓库。 按仓库首页中的安装说明操作，或下载 ZIP 后解压。保留目录结构，原型、说明和附件之间使用相对链接。
  2. 让 AI 检查并安装 Skill。 使用第 2 节的安装指令。确认它能读取 workflow-orchestrator/SKILL.md，并说明实际安装位置。
  3. 准备一个独立产品目录。 例如 D:\产品项目\个人任务系统。这是业务文件的保存位置，与解压目录、Skill 安装目录分开。路径按你的电脑修改。
  4. 发送一次明确的启动请求。 使用第 3 节的示例，给产品名称、目录、已有材料和本轮范围。没有成熟需求文档也可以从想法开始。
  5. 阅读本轮成果并回答必要问题。 优先看审核摘要、试用入口和真正需要你决定的事项。已经回答过的内容不用重新填写；不知道的事实可以直接写“不确定”。
  6. 原型可用后，从正常入口试做一个任务。 正式流程通常在 S2 起提供原型，例如创建任务、打开详情、完成后再查找它；若本轮只做 S1，先审核需求定义和竞品报告即可。看到问题时说明起点、操作、预期和实际结果，AI 据此修订并复验。

如果只想先体验页面，可以直接打开本手册附带的个人任务系统教学原型，不需要先初始化正式项目。完整练习见第 10 节。

一次完整 S1 的标准成果是需求定义书和独立竞品调研报告。资料盘点、问题单和访谈提纲是推进过程中的材料，不会自动替代这两份成果；必要依据尚缺时，成果会保留为草稿。

2 安装与可用性检查#

先确认能完成哪些工作

条件 用途 缺少时的处理
支持本地 Skill、文件读写和命令执行的 AI 客户端 读取规则、保存项目和维护版本 只有普通聊天窗口时，不能把粘贴 Skill 文本当成完整本地工作流安装
可实际启动的 Python 3.10 或更高版本 执行项目维护与校验脚本 先定位可用解释器或补齐环境；不把发现一个命令名称当作已验证
搜索与网页读取能力 研究竞品和核对现行资料 标明未检索范围，不能编造链接、价格或研究结论
可实际操作的浏览器能力 打开原型，点击、输入并记录结果 可以继续整理独立材料；尚未操作的任务不能标为实测通过
实际可调用的 /ecc:plan-prd S5 新建或实质重生成 PRD/SRS 本包不包含该原始命令；缺失时先整理输入、核查已有稿，相关新生成保持未完成

让 AI 完成安装

复制下面这段，把解压位置改成自己的实际路径。安装只需要完整的 skills/workflow-orchestrator 文件夹，不能只复制其中的 SKILL.md。

可复制指令 1
请安装这份产品需求工作流 Skill。
GitHub 仓库 ZIP 已经解压到：【完整路径】。
先检查包内文件校验清单、技能入口和当前客户端实际支持的 Skill 目录。
若已有同名版本，先完整备份并比较差异，再更新，不覆盖我的业务项目。
保留整个 workflow-orchestrator 文件夹，包括 stages、methods、references、assets 和 scripts。
安装后核对入口、本地引用、方法包完整性和 Python 可启动情况，告诉我实际位置与仍缺少的能力。
本次不要创建正式产品项目，也不要自动安装完整 ECC 或其他外部插件。

本仓库支持通过 skill-installer 的 GitHub 链接安装，也支持文件夹安装，没有一键安装脚本。当前官方文档列出的 Codex 用户级位置为 ~/.agents/skills，项目级位置为项目中的 .agents/skills。部分既有环境使用 .codex/skills，部分接收环境仍采用此路径；应先确认客户端实际发现的目录，保留仍可用的安装，不必为了路径名称迁移。避免在多个发现位置同时放置同名的不同版本。官方 Skill 文档

确认客户端识别了入口

在支持技能选择的界面查找“产品需求工作流”或 workflow-orchestrator。当前官方说明中，ChatGPT 桌面界面可通过 @ 选择技能，Codex CLI/IDE 可通过 $ 或 /skills 选择；具体以正在使用的客户端为准。新安装未出现时，先刷新或重新打开客户端，再检查实际目录。官方调用说明

可复制指令 2
请使用 workflow-orchestrator 检查使用环境，先不要初始化项目。
请报告实际读取的 SKILL.md 路径、Python 是否真正启动成功、浏览器是否能操作，以及 /ecc:plan-prd 是否有可用入口。
区分“已验证”“未执行”“不可用”，并说明这些情况各影响哪部分工作。

能看到 Skill 名称，只证明入口被发现。文件完整性、浏览器实操、外部命令调用分别核对。接收方电脑仍需自行做这次环境检查，不能直接沿用作者电脑的通过记录。

3 从产品想法启动#

给出最有用的初始信息

一段话也能开始。尽量带上：产品或功能名称、谁在什么情境遇到什么问题、本期希望改善什么、已知范围与限制、已有资料的位置，以及希望保存到哪个目录。真实案例往往比一长串功能名称更有帮助。

已知的负责人和使用设备可以一并说明；尚未确定的内容如实写未知。AI 会先读取资料、复用已有回答，把当前可识别的关键缺口集中提出，不要求你先填完所有模板。

可复制指令 3
请使用 workflow-orchestrator 启动一个新需求，先完成 S1 需求澄清。
产品名称：【名称】。
项目保存到：【完整目录】。
目标用户与问题：【谁在什么情境下，做什么事时遇到什么困难】。
本期希望改善：【可观察的结果】。
已知范围与限制：【包含什么、不包含什么、设备或既有系统限制】。
已有资料：【文件路径或已附上的材料】。
请先复用材料中的答案，集中整理必要问题；完成需求定义书和独立竞品报告的适用工作，给出可读入口、未决事项与下一步。

如果资料里出现多个互相矛盾的说法，指出哪些是最新决定、哪些只是建议。AI 应保留来源和影响，不自行选取最容易实现的一条当成已确认规则。

已有项目直接接续

可复制指令 4
请使用 workflow-orchestrator 接续项目：【项目根目录】。
先读取现有状态、当前有效成果、最新候选稿和未关闭问题，不新建重复项目。
本轮要完成：【具体目标】。
新资料在：【路径或附件】。
先说明这次从哪一阶段接续，再完成不受缺口影响的工作。

路径是最可靠的接续信息。目录下有多个项目时，选择 AI 展示的实际项目；不要只说“继续那个项目”后让它猜。已有项目采用英文目录也可以沿原位置继续，不需要先手工改名。

4 每个阶段怎样配合#

普通使用优先通过总控 workflow-orchestrator。你可以直接说“继续业务建模”或“修改这个原型”，由 AI 判断阶段和所需资料，无须记住每个子 Skill 的英文名称。

阶段 AI 的主要工作 你重点查看或决定什么 核心成果
S1 需求澄清 理清问题、目标和范围，盘点资料并研究竞品 真实事实、目标用户、本期边界及重要取舍 需求定义书 T01、独立竞品报告
S2 业务建模 梳理角色、对象、流程、规则、状态和异常，实际演练闭环 谁负责、允许什么、禁止什么、状态和资源怎样变化 业务模型 T02、图表、业务验证原型及操作记录
S3 产品方案 组织功能、页面、区域、导航和完整任务，验证业务承接 功能是否完整、入口是否合理、重要方案如何选择 产品功能方案 T03、全系统页面布局、功能验证原型及覆盖记录
S4 原型与验证 复用已有设计资料或形成具体设计约定，细化界面和交互，开展独立视觉评审与任务走查 有 UI/UX 资料时可添加；提供真实使用反馈，组织目标用户验证，处理必要品牌或业务决定 可操作原型 P04、原型与验证说明 T04、评审及验证记录
S5 需求文档与评审 经规定入口生成并整理 PRD/SRS，建立追踪和验收，处理评审 产品承诺、业务规则、研发可理解性、测试可判断性和交付范围 同版 PRD 与 SRS、T05、验收和交付记录

S1 先讲问题和证据

提出目标和范围时，尽量给最近一次实际发生的例子。遇到补问，可以按主题一次回答，例如“用户是个人；只做手机网页；不做团队；收费模式暂未决定”。不确定的市场数据和用户意愿应保持未知。

S2 检查业务结果是否闭合

可以这样提出核验任务：

可复制指令 5
请根据当前有效需求完成业务建模。
用同一笔业务贯穿各角色，说明每次动作后的对象状态、资源变化和关联记录。
制作面向用户的业务验证原型，实际检查正常、拒绝、重复和重要异常路径。
没有依据的规则集中列出；已明确的路径继续验证，不替我决定未知业务。

例如“审批通过”可能同时要求单据变为已通过、库存减少、审批记录生成。只弹出“成功”不能证明这三项结果都成立。

S3 查看完整任务和系统页面

可复制指令 6
请基于有效业务模型完成 S3 产品方案。
展示本期各角色入口、完整页面布局和连续任务，原型要呈现一个可供用户操作的应用。
把关键任务和规则对应到页面区域、控件与状态，检查返回、取消、异常及跨页数据一致性。
普通布局由你自主设计；需要业务或重大方案决定的事项集中说明。

试用时从首页完成任务。关注要找的信息是否能找到、操作后是否得到完整结果、切换页面后是否仍能继续，而不只看单个按钮有没有响应。

S4 先核对设计依据再细化

已有 UI/UX 规范、设计稿、组件或实际页面时，可以添加供 AI 复用；没有时可以暂不添加，不必先编写或上传一套规范。AI 会依据有效 S3 成果、目标设备及可复用界面，形成可核对的布局、字体色彩、组件与反馈约定，标为“AI 暂定设计基线”，继续制作原型。常规选择无需逐项批准，也不能冒充已获正式品牌认可。

明确要求遵守的 VI 品牌资产或标准、现有规范冲突，以及未定的业务规则或权限，仍按实际影响处理；AI 只集中提出确实需要人解决的事项。独立成品评审会对照实际采用的标准或 AI 暂定基线，任务操作和真实用户验证仍分别进行。以后补充 UI/UX 资料时，先核对差异，再更新受影响的设计记录和原型并复验相关任务，不因此重做无关页面。

可复制指令 7
请接续当前 S3 成果进入 S4，已有 UI/UX 资料：【有则填路径，没有则写暂无、暂不添加】。
先核对本期页面、状态和设备所需的设计依据；普通布局、组件和视觉选择由你完成。
没有 UI/UX 资料时，依据有效 S3 和现有界面形成具体的 AI 暂定设计基线并继续，不要求我先补齐规范或逐项批准常规选择。
必要品牌要求、规范冲突或业务规则缺口请说明具体影响；不要把暂定设计写成正式品牌认可。
制作原型后分别报告独立视觉评审、实际任务操作和真实用户验证的情况。

AI 代理、专家审阅和浏览器自动操作不等于目标用户亲自试用。真实用户验证需要具体任务、实际观察和反馈；低风险豁免也须由有权负责人明确给出范围及依据。

S5 使用有效成果形成双文档

可复制指令 8
请基于本项目当前有效的上游成果生成配套 PRD 和 SRS。
先核对当前环境实际可调用的 /ecc:plan-prd 定义和入口，按规定执行并保存输入输出记录。
随后整理十一章 PRD、展开六章 SRS，检查规则、状态、权限和验收是否一致。
已有适用信息直接复用；新发现的业务或功能变化先回对应上游处理。
如果命令不可用，明确未执行及受阻部分，继续整理输入和核查已有资料。

/ecc:plan-prd 先负责 PRD 生成入口，SRS 再依据有效 PRD 和上游规则展开。原始命令未定义直接生成 SRS。本地“能力约束与规格”方法只是辅助核查，不能替代这次调用。适用历史执行可复用；纯错字、排版或链接修复通常不必重跑命令。

5 三种原型分别看什么#

S2、S3、S4 都应有面向用户的应用入口、页面和连续任务。它们的主要区别是验证目的；S2/S3 同样应当直观可用，可以采用标明用途的演示样式。

原型 用个人任务系统举例 重点判断
S2 业务验证原型 创建任务后是待办，完成后是已完成，恢复后回到待办；取消规则依有效决定执行 状态、规则、角色和业务结果是否正确
S3 功能验证原型 用户从列表找到任务，进详情处理，再返回原筛选；多个页面读写同一任务 页面与功能是否承接业务，完整任务能否走通
S4 原型 按设计依据呈现信息、按钮和反馈，检查目标设备，并观察真实用户能否完成任务 呈现和交互是否正确，规范与实际使用是否匹配

调试按钮、角色切换、故障注入和覆盖报告放在独立演示设置中，不应成为产品默认首页。三个阶段可以复用适用的界面和交互，不要求永远使用同一个 HTML 文件。S2/S3 的演示样式也不会自动成为 S4 的正式品牌标准。

6 阅读成果与试用原型#

新项目优先从项目中的 06-项目管理/查看与试用.html 阅读。它汇集已登记的文档、同版原型、页面布局、操作记录和 SRS，并区分有效版本与候选稿。局部工作尚未登记时，使用 AI 直接给出的工作稿链接。

建议先看本轮审核摘要，再实际试一个任务，最后按需要查看依据。若 AI 只给了路径或长篇台账，可以这样要求：

可复制指令 9
请给我本轮的直接阅读和试用入口，并说明改了什么、沿用哪版依据。
给一个从正常入口开始的代表任务，写清步骤、预期结果和实际检查情况。
最后只列本轮确实需要我决定的事项，以及不受这些事项影响、你可以继续完成的工作。

正确理解状态

看到的状态或说法 可以据此判断什么
已生成或候选稿 有可阅读的成果，尚不能据此认定已确认或生效
内部检查通过 所列自检已执行；仍需看检查范围，不能替代真人验证或授权
待决定或待补资料 有具体事实、规则或资料缺口，应说明影响和承接人
待验证 对应任务尚无足够实际证据，不应写成通过
待授权 内容及必要检查已具备，仅缺实际有权人的决定；若仍有关键缺陷，不能只概括为待授权
当前有效版 内容版本已按要求生效；正式复用仍需检查授权和影响记录是否适用
已交付 应能定位获批清单、实际包及包内检查记录，不能仅凭生成 ZIP 判定验收完成

有异常时，按“从哪里开始—输入什么—做了什么—预期—实际”描述。可以附页面或文件位置，但不必先猜根因。

可复制指令 10
项目：【路径】。原型版本或入口：【实际位置】。
我从【起点】输入【内容】，执行【操作】。
预期：【应看到的结果】；实际：【实际结果】。
请定位原因、保留旧版，修复后实际复测这条任务及受影响的返回或异常路径。

7 修改需求与同步上游#

S4 发现的问题也会回到它所属的来源阶段。AI 应先判断改动性质，再更新受影响的依据、原型和已有下游文档；不是每次调颜色都重写需求书，也不能只改页面就当业务变更已经完成。

改动举例 先处理的来源 后续需要核对
从个人使用扩展为团队协作 S1 目标与范围 角色、规则、功能、原型及已有 PRD/SRS
修改取消资格、审批权限或扣库存时点 S2 业务规则 相关任务、状态、页面、交互与验收
新增一个操作或改变任务路径 S3 功能行为 页面布局、实现映射、原型及已有双文档
已定功能的按钮遮挡、间距或反馈呈现错误 S4 呈现和实现 对应设计记录、页面区域及受影响交互
PRD 错字、链接或表述不清 S5 文档表达 同版引用和对应 SRS，确认没有暗改产品承诺
可复制指令 11
请修改项目：【项目路径】。
当前入口或版本：【实际位置】。
我希望把【现状】改为【目标】，原因是【背景】。
请先判断变化属于目标范围、业务规则、功能行为还是呈现。
必要时先修对应上游，再同步受影响的原型、记录和已有 PRD/SRS；保留旧版及稳定页面标识。
不要重做无关页面，完成后给出改动清单、实际复测结果和仍待决定的事项。

如果 PRD/SRS 尚未生成，AI 应更新已经存在的上游成果，并记录后续生成需要采用的依据；没有文档时不应声称已同步过文档。涉及新业务取舍时，需要真实决定后才能让修订生效；工作稿可先准备，不能暗中替代有效版。

只做一个小改动

可复制指令 12
这次只修复【页面或任务】的【具体问题】，不扩大产品范围。
请读取现有实现和依据，保留旧稿，修改受影响区域并实际复验。
交付可打开的成果、简短改动说明和检查记录；无须为本次局部试用重新初始化五阶段项目。

局部试用不需要机械补齐整套台账。若后续要形成正式阶段成果或交付，再复用这些草稿和真实证据，补齐登记及适用检查。

8 继续工作与团队交接#

换一个聊天或由同事接手时，交出项目根目录、当前可读入口、本轮目标、未决事项和实际负责人信息。项目文件保存了版本和接续位置，聊天摘要仅作为补充。

可复制指令 13
请继续项目：【项目根目录】。
先从项目文件读取当前有效版本、候选稿、最近检查、待决事项和下一动作。
本轮重点是：【目标】。
沿用仍适用的决定，不重复询问已确认信息；报告真正缺失或已经失效的部分。

一个项目的多人修改应由团队协调当前维护人；别人正在写入时，不要通过手改状态文件或清锁来“加速”。读文档和整理意见可以并行，正式更新应保持同一份项目事实。

怎样给出清楚的决定

当你确实有相应职责、已经看过具体成果时，使用包含对象、版本和范围的回复。下面是表达结构，不是预先批准：

可复制指令 14
我作为本项目【实际职责】，已阅读并试用【成果及实际版本】。
对本轮待决事项【问题名称】，决定采用【结论】，适用范围是【范围与条件】。
对【阶段及版本】的交接意见是【同意进入下一阶段／修改后再审】。
仍需处理：【如有，写具体事项；没有则写无】。

阶段继续决定和正式交付批准分别对应实际对象。不要用一句“以后都自动通过”代替后续未确定版本的审核。已经给出的决定仍适用时，AI 应直接复用，不重复索取。

9 专业方法怎样参与#

新增方法由阶段根据任务自动选择。使用者一般只需描述目标和约束，不必逐个点名，也不必安装所有上游框架。

方法 什么时候会用 结果放在哪里
研究证据 research-evidence 复核研究结论，按需诊断目标或准备访谈 原有竞品报告、需求定义和来源记录
任务组织 task-solution 功能零散、大功能需要拆分、行为不清楚 产品方案、功能与页面映射
场景覆盖 scenario-coverage 多角色、异常、多对象结果或变更回归需要查漏 原有场景、验收和质量记录

有选定图片或 Figma 设计时，可在工具确实可用、输出适配当前 HTML 交付的前提下使用对应设计 Skill。没有参考图也能依据现有方案完成设计，不必每次选三套风格。可选工具不可用时可继续适用的本地工作；S5 必用的 /ecc:plan-prd 仍按其专门要求处理。

10 用个人任务系统练习#

打开教学原型。这是已有案例的独立教学副本，包含四条初始样本。数据仅在本次打开期间共享，刷新会恢复初始数据，不连接生产后端。

建议先按以下顺序体验，理解如何把反馈说清楚：

  1. 在“已取消”筛选中点击“新建任务”，先留空标题提交，观察提示；再填写标题和备注，确认新任务能被看见。
  2. 打开新任务详情，修改并保存备注，返回后核对列表摘要，再重开确认内容一致。
  3. 在待办筛选下打开“准备周报”，标记完成并返回，核对原筛选仍在；切到已完成确认任务可找到。
  4. 恢复一条已完成任务，取消一条待办任务；查看状态说明与可执行操作是否一致。
  5. 缩窄浏览器窗口，阅读长标题和完整备注，滚动到详情底部，确认操作可达。窗口缩窄不等于手机真机验证。

需要练习失败反馈时，打开页脚“演示设置”，开启下一次提交模拟失败，再回正常页面保存备注。检查输入是否保留、旧数据是否没被写坏、重试后是否得到结果。这里的模拟失败不证明真实网络服务已经实现。

试过之后，可以让 AI 在另一份副本上做一次小改动：

可复制指令 15
请使用 workflow-orchestrator 做一次隔离教学练习。
输入是：【教学原型完整路径】。
请先复制到：【独立练习目录】，保留原始案例，不写入正式项目。
本轮只把新建任务的空标题提示改成更容易理解的文案，不改变必填规则。
完成后实际检查空标题仍被拦截、正常创建成功、详情编辑及返回筛选仍可用。
给我新副本入口、改动说明和实际检查结果；不要把练习记录当成真实项目批准。

另行分发的历史分享包含旧版教学项目和验证资料，本 GitHub 仓库不包含这些历史资源。本节副本包含新建、备注及取消状态，旧版“个人任务完成与恢复”是不同范围的案例，不能把两者拼成同一版业务规则。历史文件中的 TEST 角色、批准和演示数据不能直接沿用到真实项目。

11 常见问题与处理方式#

找不到这个 Skill

让 AI 检查实际客户端、发现目录、重复安装和 SKILL.md 路径。仅把文件上传到聊天中不等于本地安装。若新安装未显示，刷新或重新打开客户端后再检查。

AI 反复问已经回答的问题

给它已有回答的来源或文件，让它先复用，只列新增冲突和必要缺口。可以直接说：“请把已知、未知、冲突和可后置项分开，合并本轮需要我回答的问题。”

我只是想改一个页面却启动了整套流程

明确本轮是局部修改，并给旧版入口与目标。最小成果是可打开的修改稿、简短说明和实际检查；正式交接要求只在相应任务需要时补齐。

S2 或 S3 还是只有几个孤立按钮

要求按当前有效范围补齐默认用户入口、导航、完整页面、跨页共享数据和任务返回，把评审工具放到独立入口。不要为了“看起来像 App”加入未确认的账号、消息或其他业务。

原型显示通过但任务走不通

让 AI 区分结构检查、实际操作和真实用户验证。提供能复现的步骤，要求保留失败记录并从正常入口复测；截图或脚本解析成功不能代替操作结果。

没有 UI/UX 资料或品牌规范能否继续 S4

没有 UI/UX 资料可以暂不添加。AI 复用有效产品方案、已有页面与组件，补齐具体的暂定设计基线后继续；仅缺用户提供的 UI/UX 文档不构成阻塞，也不需要为常规布局另行批准。后续提供资料时，只更新受影响的设计和原型并复验。

品牌要求需单独判断：已有且必须遵守的 VI 标准或必要资产不能擅自替换，冲突或必要缺口要说明影响和解决方式；没有正式品牌要求时，使用标明性质的暂定设计，不声称正式品牌符合。业务规则、权限及真实用户验证的要求不因资料可选而改变。

没有真实用户能否写验证通过

不能用 AI 自测代填真人结果。可以记录已完成的任务检查，继续准备验证计划；适用的低风险豁免需要有权负责人作真实决定，并限定范围与依据。

/ecc:plan-prd 不可用怎么办

先确认当前宿主中是否存在真实入口及所需定义。该名称不是 PowerShell 命令；下载一份说明或读过本地方法也不等于执行。缺少入口时保留未执行状态，继续整理输入或核查已有文档，由维护人员补齐依赖后再完成相关生成。

想直接跳到 S3 或 S4

可以直接提出目标，AI 先判断已有资料是否足以支持，并复用有效成果。缺上游规则或功能依据时，补的是受影响部分；不能从现有页面反推所有业务已经确认。单页教学试用与正式阶段生效分别记录。

文件打开失败或显示的不是最新版

从管理入口及状态索引核对当前有效版、候选稿和同版附件，不按文件修改时间猜。浏览器不允许本地文件链接时，让 AI 使用环境允许的本地预览方式并说明限制，不绕过浏览器安全提示。缺文件或哈希变化应先定位原因，不能直接写成正常。

怎样把项目交给研发

让 AI 准备当前版本的 PRD、SRS、原型、验收和来源清单，组织实际评审，处理阻塞意见，再取得对应清单的交付批准。导出后从包内入口检查文档、原型和附件；只有包内验收完成，才报告本次交付验收完成。

12 文档格式与文件位置#

业务正文默认使用中文 Markdown，原型默认 HTML/CSS/JavaScript。流程图保留可编辑 draw.io，重要图配 SVG/PNG。你可以另行要求阅读用 Word 或 PDF 导出；导出版应注明来源版本，不成为第二套业务事实。

目录 通常在哪里找内容
00-项目资料 产品基本信息、原始资料与参考材料
01-需求澄清 竞品调研、需求分析、需求定义
02-业务建模 业务模型、流程状态图、业务原型和记录
03-产品方案 功能规格、全系统页面布局、功能验证原型
04-原型验证 交互原型、视觉依据、评审及验证记录
05-PRD交付 PRD、SRS、评审成果与交付包
06-项目管理 查看与试用入口、状态、版本、变更和交接视图

并非每个子目录都会在第一轮出现。按实际成果逐步形成；已有英文布局沿原路径接续。你无需手工编辑 state.json、维护 JSON 或填写程序参数，AI 通过脚本完成维护。

PRD 与 SRS 的结构

PRD 十一章：文档定位；背景与问题；产品目标与成功标准；用户与权限；范围与主流程；功能需求；通用质量与业务约束；交付里程碑；待决事项；风险；来源索引。

SRS 六章：能力概述；约束与不变量；实现契约；范围边界；待决事项；交接结论。

PRD 主要帮助团队理解产品承诺和范围，SRS 展开研发需要理解、测试能够判断的具体行为约束。两者按同一版 T05 管理，引用同一批有效规则和待决项；不是两份各自更新的需求书。

常见编号

编号 含义
T01—T05 五阶段主成果；T05 管理配套 PRD/SRS
P04 S4 原型成果
R D Q 评审、决定和质量记录
SCN RULE FUN PAGE 业务场景、规则、功能、页面的稳定定位
REQ AC DEC 需求、验收条件、待决事项的追踪定位

编号用于追溯和定位，不要求使用者先学会编号才能提出任务。正式成果打开 AI 返回的实际登记路径，不自行改名、覆盖旧版或把候选稿替换为有效版。

13 团队日常使用约定#

每个真实产品使用独立项目目录，明确实际维护人、业务决定人和交付负责人。资料放回项目并注明来源；重要决定写清适用版本和范围。同事交接时共享项目文件及入口，不仅转发聊天截图。

评审时优先提交可复现的问题和业务理由。对 AI 的建议明确写“采纳”“修改后再看”或“尚未决定”，避免把讨论意见误当成最终规则。普通设计和文字维护让 AI 自行完成，团队把精力放在事实、取舍和实际使用结果上。

更新 Skill 时，保留旧版安装和项目备份，检查已有项目的接续、原型入口及外部依赖。Skill 更新不表示历史成果自动重新通过，也不要求所有项目从 S1 重来。
