# S4 视觉资料准入与独立成品评审

本协议区分两个关卡：A01 判断资料能否支持后续原型开发；A03 完成后比对规范与实际页面。A01 没有已实现页面时不做成品评价。两个关卡都不代替 A04 功能走查、A05 真人验证或有权人员的交接决定。

## A01：资料可选补充，设计依据就绪后开发

读取最终有效 T03、系统页面布局、S3 功能验证原型与功能覆盖记录、相关 T02/RULE 及目标平台。S3 功能验证原型用于核对任务和功能完整性，可复用其适用界面、组件及已验证交互；核对展示依据和正式要求差距，演示样式不自动成为 S4 品牌标准。采用 [资料准入模板](../assets/templates/visual-material-readiness.md)，先列本期页面、关键状态、主要用户任务及目标视口，再判断需要哪些资料。

“最小视觉交付单元”是本期一个可完整表达的任务或页面组及其关键状态和目标平台，必须有足够依据确定外观、交互反馈和适配方式。它是判断资料充分性的覆盖单位，不要求在 A01 先制作代表页。多个单元可以复用同一资料；不要求每类都提供独立文档，也不因文件齐全就认定内容充分。

按实际范围检查：

| 材料范围 | 需要能核对的内容 |
| --- | --- |
| VI 与品牌资产 | 品牌标识、图片/图标及可用文件，使用场景、留白/背景和禁止用法；没有品牌要求的项目写明依据 |
| 字体与色值 | 字族/字重/层级、实际可用字体和回退约定，品牌色、语义色及使用场景 |
| UI 组件与版式 | 页面框架、栅格/间距、主要组件和适用状态、内容密度与层级 |
| UX 规则 | 导航和任务路径、主次操作、输入校验、加载/空/失败/成功反馈、取消/返回/恢复行为；业务含义仍以 T03/T02 为准 |
| 平台与可访问性 | 本期设备/视口、响应式或平台差异、键盘/焦点、文字可读性、重要反馈表达等约束与检查范围 |

用户提供的 UI/UX 资料是可选输入。先复用已提供的规范、组件库、页面、截图或文字说明，核对版本、范围和冲突；未提供时可提示“已有 UI/UX 资料可添加，没有可以暂时跳过”，不等待答复、不反复索取，也不要求用户先编写规范。用户明确没有或暂不添加时，记录“未提供／可后补”，不能仅因此判 not-ready。

没有现成 UI/UX 资料，或仅有部分资料时，AI 根据有效 S3、目标设备和已有页面补足常规呈现选择：字体/色值、布局/组件、导航、关键状态反馈与适配范围。将具体可核对的基线及理由写入 T04 的[设计约定](design-and-mapping.md)或同版附件，在 A01 引用足以开工的基线，A02 再细化页面映射。标明“AI 暂定设计／待后续资料校准”，无需另取临时样式批准；记录来源为 AI 设计，不伪造用户确认或正式 UI/UX 标准。截图中推断的数值同样标推断。不能仅写“使用默认样式”而没有具体依据。

只有 AI 无法自行解决的真实阻塞才集中补问：项目已明确必须遵守却不可访问的 VI/品牌资产、有效规范相互冲突、重要产品取舍或上游业务定义缺失。每项说明影响、可接受补充形式和责任人；缺失功能/规则回 S3/S2。既有正式标准仍优先，有意偏离其强制要求须有实际适用决定。没有既定品牌要求的范围可使用 AI 暂定设计，不因此新增索取 VI 的通用要求。

常规设计选择不增加逐项人工审批。需要改变已定品牌要求、业务行为或超出授权范围时，建议仍不等于批准；复用适用的已有授权。后续补充 UI/UX 资料时，先核对来源、版本和差异，更新同一设计约定及受影响映射，保留旧版、局部修改并复验相关任务；不无差别重做整个原型。

给出 `ready` 或 `not-ready`：

- `ready`：每个本期单元有足够的既有标准或具体 AI 暂定设计，关键冲突已解决；可选 UI/UX 资料未提供可列为非阻塞后补项。有意偏离强制要求的部分已有适用决定。记录依据、版本、来源性质、适用单元及剩余限制。
- `not-ready`：明确必需的品牌资产不可访问、强制规范冲突未解决，或关键业务/功能定义仍缺失。说明实际阻塞，不能以“用户没上传 UI/UX”代替理由；受阻范围不进入 A02/A03，可继续独立准备或划清范围后的非受阻任务。

不得生成不存在的品牌资产、伪造标准或把方案建议登记为用户决定。已提供的品牌字体可用时优先按该标准实现；离线打包或字体不可用时说明影响并取得适用回退约定，不能以自包含 HTML 为由强制用系统字体覆盖品牌。

## A03 后：准备可独立判断的评审材料包

原型实现达到本轮评审范围后，按 [评审材料包模板](../assets/templates/ui-finish-gate-packet.md) 冻结独立包。至少包括：

1. A01 ready 记录、适用的现有标准/实际资产及具体 AI 暂定设计基线；明确正式、AI 暂定、经实际决定的偏离和不适用范围与版本。没有用户 UI/UX 文档时以设计约定作为 standards，不虚构资料或批准。
2. 当前原型 HTML/必要资产、P04 候选版本、可打开方式、本期页面/状态/关键任务、有效行为依据及目标平台/视口。
3. 实际渲染的目标页面、关键状态和目标视口截图；每张标明原型版本/哈希、页面、角色/状态、实际视口宽高、滚动位置、截图模式及获取方式。图像像素尺寸与 CSS 视口不同要说明；弹窗保留实际视口截图，长内容保留可定位的上下文或连续片段。截图保存后实际打开核对，不能把裁切、全页合成异常或未生效的视口设置当成实现证据。
4. 适用品牌参考或 AI 暂定设计条目与实现截图的并排证据，或可逐项定位的参考/实现配对索引，覆盖资产、字体、色值、组件与版式。没有品牌参考时不强求用户补一张图；基线条目与实际截图配对可作为 comparison。源代码数值可辅助核对，不能替代视觉查看。
5. 有意偏离的理由、范围、决定来源和状态，明确“已批准”或“待决定”；待决定偏离不能因写进材料包便视为接受。
6. 已存在的真实操作或真实用户观察/豁免原始证据（若有），以及没有这些证据的范围。只提供事实材料，不把作者自评写进评审输入。

冻结包用实际相对路径和 SHA-256 记录标准、实现、截图、对照证据，能回到本次文件版本。网页素材须保存适用快照或可复查依据；不可访问的参考标缺失。不要把主观“效果良好”、作者希望的结论、开发聊天或上轮评审意见带入独立包。

## UI Finish-Gate Reviewer 的独立执行

调用新的独立代理，设置 `fork_turns="none"`；其他环境须有等效的真实上下文隔离。角色名为 **UI Finish-Gate Reviewer**。不能由本轮实现代理改名兼任，也不能把开发聊天清空后的自评冒充独立审阅。启动消息仅给本协议的评审要求和冻结包入口，不给作者自评、期望判决、上一轮结论或意见。记录真实会话/代理标识、输入包及实际使用的工具。

评审者必须实际打开适用标准/AI 暂定设计基线和对应实现截图，记录看过哪些配对、发现什么；有品牌参考时一并查看。基线是可检查的输入，不是作者自评。若需补充截图，由执行者从冻结实现版本获得并补齐包后再评；不要凭文件名、CSS 值或作者描述认定视觉一致。平台范围只按实际视口和证据判断，未测范围明确待检查。工具不可用、资料不可读或缺必需截图时保持“评审未执行/证据不足”，说明补齐动作；不能伪造会话或通过结论。已实际审阅且确认材料存在阻塞时可以给有具体依据的 no-go。

输出使用 [独立评审模板](../assets/templates/ui-finish-gate-review.md)，仅有两个主部分 **结论** 和 **意见**。结论先给本关卡 `go`、`no-go` 或 `conditions-go` 及依据，再分别写清：

| 结论类别 | 在此关卡判断什么 | 与原检查表的关系 |
| --- | --- | --- |
| 功能 | 已观察的操作/显示范围、与方案的关系；A04 未做的全量操作仍待检查 | Q04-01 任务覆盖、Q04-02 可操作、Q04-03 方案一致 |
| 品牌视觉 | 素材、字体、色值、组件、版式与适用依据的逐项对照；使用 AI 暂定设计时只判断该基线的实现质量与一致性，不能声称正式品牌已符合 | Q04-03 方案一致、Q04-06 版本与结论 |
| 平台适配 | 本期平台、目标视口和状态下的布局/操作表现，未测适配限制 | Q04-01 覆盖、Q04-02 可操作、Q04-03 方案一致 |
| 用户验证 | 真实观察或有效豁免的存在与范围；无实际依据写 pending | Q04-04 验证真实性 |

四类各写范围、状态、证据和局限，意见处理对应 Q04-05，所有类别的版本与适用性对应 Q04-06。保留 Q04-01—06 原编号及真人验证要求。此关卡总体 go 仅表示本次冻结范围的 UI 成品评审可放行；不要求把尚未发生的 A04/A05 填成 pass，更不能凭专家观点标记用户已验证。

## 三种结论的处理

| 结论 | 下一步与放行依据 |
| --- | --- |
| `go` | 该冻结版本的成品关卡通过，进入 A04。不存在阻止本关卡放行的必改意见；建议可记录，不冒充待满足条件。 |
| `no-go` | 根据具体意见修订，保留旧包/判决，形成新版本后交新建的无上下文专家再次评审。没有固定最大轮次；缺素材、工具、授权或不能取得新证据等真实阻塞要记待补，不在同一缺口上空转。 |
| `conditions-go` | 固定本轮具体、可验证的必改意见；执行者一次落实本轮修改，并逐条记录完成证据后通过，不新开专家评审。核对原条件是否已做到是修改完成核对，不重新评审、不添加新意见开启第二轮。未实际完成任何原条件则保持待完成/阻塞。 |

go 要求品牌视觉已通过、平台适配已通过或有具体不适用依据；已知未解决的视觉/平台阻塞不能用 conditions-go 掩盖。conditions-go 的必改项必须有定位、问题、具体修改和可核对验收条件；“更好看”“继续优化到满意”不能作为有限条件。保存原报告哈希、本轮意见 ID、一次修改后的完整文件版本/哈希及每项实施证据，绑定原包与结果。不得重写原意见降低标准，也不得悄悄修改标准文件以宣称已完成；若条件必须依赖新授权/新资料，记录阻塞并取得实际解决依据。

新范围、新标准或本轮条件之外的新增需求另立任务版本并重新确定适用评审，不借本轮结论放行。修改引入功能缺陷仍须按 A04/A06/A07 处理；任何视觉关卡结论都不能绕过功能门禁、真人验证和实际交接决定。

## 保存与结构核验

A01 记录、冻结包、参考/截图对照、独立报告和条件修改证据作为 P04/T04 附件保存快照。P04 refs 指向实际上游与任务，T04 refs 指向确切 P04，不建立双向循环。评审后的原型变化须判断旧结论适用性：conditions-go 仅覆盖固定条件对应的那次修订；其他改变需新的适用结论或明确未影响依据，不把旧评审自动套给新版。

辅助脚本 [ui_finish_gate.py](../../../scripts/ui_finish_gate.py) 只核对 JSON 结构、文件哈希和处理分支，不能证明实际查看、上下文隔离、审美质量、真人观察或授权真实性。必须同时保留真实执行记录。Markdown 保留“结论 / 意见”两部分，报告 JSON 作为附件；完整字段和 CLI 见 [本地命令](../../../references/local-tools.md)。命令形状：

```text
python <skill-root>/scripts/ui_finish_gate.py --help
python <skill-root>/scripts/ui_finish_gate.py --root <项目目录> --report <评审JSON>
python <skill-root>/scripts/ui_finish_gate.py --root <项目目录> --report <原评审JSON> --fixes <本轮修改JSON>
```

结构使用 schema_version=1；reviewer 记录实际独立会话，packet 绑定 ready 的资料版本与原型版本，并提供 standards/implementation/screenshot/comparison 四类实际文件及哈希；conclusions 含本关卡判决及四类结论；opinions 保留意见及验收条件。前三类状态为 pass/fail/pending/not-applicable/conditions，user_validation 仅 verified/waived/pending。go 不含 required 意见，其他两种判决须有具体 required 意见。仅 conditions-go 使用 fixes：round=1、report_sha256、packet_id、原必改意见的完成证据和 after_files；标准保持原哈希。无法实际执行时明确未执行，不把模板或脚本解析成功当成专家评审通过。
