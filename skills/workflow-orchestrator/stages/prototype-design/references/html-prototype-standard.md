# HTML 原型、操作证据与版本规范

## 载体与范围

开发前必须有 A01 ready 记录，具体见 [视觉资料准入与成品评审](visual-readiness-and-finish-gate.md)。默认生成可直接打开的自包含 HTML：必要 CSS/JavaScript 内嵌，展示与交互不依赖联网 CDN、外部框架或业务后端。优先落实已提供且可用的品牌字体和资产，可按其使用要求内嵌或作为明确随附的本地依赖；不能强制系统字体覆盖品牌标准。确有不能离线使用的资源时记录影响与适用回退约定；用户 UI/UX 资料未提供时，按 A01 形成具体 AI 暂定设计基线即可继续，不为常规选择另取批准；只有明确必需品牌约束或其他真实阻塞未解决时，相依范围回 A01 not-ready。无需把 Figma 设为前置条件。

原型实现来自当前有效 T03、系统页面布局、S3 功能验证原型与覆盖记录及 FUN/PAGE/RULE 的任务、信息、权限和状态。缺失的关键企业规则回 S2、功能行为回 S3；不要在代码中用“常见默认值”补定。S4 按已准入的视觉/交互标准打磨；简化项须在适用范围内明确记录，优先复用上游适用界面及已验证交互，但不以上游展示完成度代替 S4 品牌对照，也不能省略必要任务行为。

把入口、主操作、反馈、结果、退出/返回连接成可走通的流程。按钮、表单、选择、对话框和导航使用实际事件，操作后有可观察的状态或结果。未实现区域标明演示范围，不能伪装成可用主要功能。普通内部走查不是正式可访问性审计，但操作入口应可识别、控件有清楚名称，重要反馈不只依赖颜色。

## 生成前设计与结构定位

A01 ready 后先按[设计与实现映射](design-and-mapping.md)确定设备、布局、导航、视觉与组件用法和依据，记录于 T04 §2 或同版附件；从有效 S3 保留已定信息含义/层级、操作顺序、权限和状态。按[结构规格](page-structure-spec.md)将任务/规则对应到 PAGE 内稳定区域、控件与状态，再生成 HTML。字段、标记及校验命令以该规范为准，结构标识不作为用户文案显示。

引用、重复标识、必需区域及状态声明的自动检查可提前发现内部不一致；隐藏元素或模板中存在标记仅证明结构声明。动态区域仍须从产品入口触发，在真实浏览器观察信息、权限、反馈和布局，不能用静态通过替代正确实现证据。

## 示例、外部响应与演示控制

- 在原型可见处标明“交互原型 / 示例数据”，并在外部调用被模拟的位置说明“模拟结果”；示例金额、账号、名额和记录不冒充真实业务数据。
- 用已批准行为模拟请求成功、失败、处理中或业务拒绝；记录哪些只是演示。不能写“已真实退款/发送/同步”等会让人误认真实执行的结果。
- 演示角色切换、状态重置、失败注入等放在单独标记的“演示设置”区，与产品任务入口区分；T04 列出这些控制不属于产品功能。
- 演示设置只建立初始条件或可重现的外部响应，之后仍用产品入口点击/输入完成任务。不要以“直接成功”按钮、修改 JavaScript 变量或手动跳到完成页替代关键操作链。
- 内存状态或本地演示存储的行为需明确：刷新、返回、重置后是否保留输入与结果。重复动作、取消、失败重试、权限变化等按有效规则实现，不把每次点击都做成无条件成功。
- 验证数据可重复重置，失败场景应可稳定复现；不必为制造变化增加实际外部调用或生产数据写入。

产品页面用用户理解的任务语言；演示信息和测试设置集中说明，避免把维护脚本字段、门禁术语等放进产品操作路径。

## 实际浏览器操作

先读当前可用浏览器/计算机工具和相关技能说明，再选可用方式打开 HTML；工具名、API、浏览器/标签标识由当前环境发现，不写死。原型可用文件方式打开；需要时使用仅提供本地静态文件的临时预览方式，它不提供业务后端能力。预览限制到原型目录与本机，记录实际地址与入口。

内部走查至少覆盖本期关键正常路径，以及与其相关的取消/返回、失败、重复、权限和其他关键状态。准备初始数据后从正常入口真实点击、输入或提交，并核对操作前后状态和可见反馈。使用浏览器可访问性/页面定位能力时按其允许的调用方式执行；源码检查和脚本状态读写不能代替用户式操作。

记录：

1. 原型 P04/HTML 版本、输入方案/规则、浏览器或工具环境、文件/预览地址。
2. 任务 ID、角色、初始数据/状态、演示设置与预期结果。
3. 实际逐步操作、可观察的结果、截图或可定位页面状态、问题与差异。
4. 未执行范围、工具故障及限制；修改后的再次操作和结果。

每条适用记录同时定位到同版规格的 PAGE/区域/控件/状态，核对必要信息的含义和层级、任务操作顺序与目标视口表现。权限检查观察允许和拒绝两侧；布局检查观察实际阅读顺序、内容遮挡及重排后的输入/状态保持。引用结构报告时单独说明其静态范围，不把报告中的覆盖等同于实测覆盖。

静态图片只能证明显示，合法 HTML 只能证明结构，代码断言只能证明被执行的代码路径；它们都不能单独替代实际浏览器任务完成证据。若工具不能操作，保留未检查状态，不声称通过。

## 品牌参考与页面实现的实际对照

A03 实现后、A04 全量功能检查前，用实际打开的当前 HTML 获取本期页面、关键状态和目标视口截图。将适用品牌素材、字体、色值、组件/版式的参考或 AI 暂定设计条目与实现并排呈现或建立清晰配对，保留截图版本、目标视口、正式/AI 暂定标识以及有意偏离的理由与批准状态。

按 [独立评审协议](visual-readiness-and-finish-gate.md) 由无开发上下文的 UI Finish-Gate Reviewer 实际查看对照并给结论。缺参考、缺截图或工具不能查看则记录待补；静态结构检查和哈希校验不能替代视觉审阅。完成对应判决处理后进入 A04，仍须实际操作关键任务。

## 保存 P04、T04 与证据

明确区分可变工作稿和版本文件。新业务项目使用以下中文路径，已有英文项目沿用原布局：

```text
04-原型验证/交互原型/<prototype-key>/v1.html
04-原型验证/交互原型/<P04-ID>/v1.md       共享 put 生成的入口/版本说明
04-原型验证/验证记录/<T04-ID>/v1.md       共享 put 生成的 T04
04-原型验证/视觉标准/资料准入-v1.md
04-原型验证/视觉评审/第1轮/              冻结包、参考/截图、报告和本轮修改证据
```

prototype-key 使用实际项目短标识，不推断平台 ID。已登记 HTML 不直接改写；修订为 v2.html，并保留 v1 及其当时证据。正文链接按所在文档目录计算，报告实际可访问的路径。

登记顺序：

1. 保存并快照实际来源；必要 TASK 条目引用有效 T03/FUN/PAGE/RULE。
2. 生成 HTML，按 [P04 模板](../assets/templates/p04-prototype.md) 写说明工作稿。正文提供可点击的 HTML 入口。命名入口或多文件原型按[同版登记方法](../../../references/registered-review.md#s4-原型入口与资源同版登记)使用 review_bundle，逐项登记 prototype 入口和 support 本地资源，保留相对目录。单个自包含 HTML 也可 snapshot 后用 evidence.kind=source 登记，正文从最终登记目录正确链接真实快照；locator 指明原型入口/任务区域。HTML 附件是生成物，不是企业规则已确认的来源。
3. put P04，refs 使用实际采用的方案、规则、TASK 版本。脚本在保存前核对正文到已登记 HTML 的入口、本地引用闭包和文件映射，保存后及门禁/交付时复核哈希；缺失或仅存在于工作区但未登记的资源会被拒绝。成功后从返回的登记版正文实际打开原型。静态检查不执行动态加载或交互，不代替可操作性检查；失败修正工作稿后重试，不补写已登记版本。
4. 固化 A01 资料准入、当前独立评审包/报告与判决处理证据，绑定实际标准、HTML、截图和对照文件版本。conditions-go 保留原报告与一次修改后的完整文件清单，不重写原报告替代完成证据。实际浏览器操作记录用 snapshot 固化，I/V 检查引用 operation 证据；不要拿生成的 HTML 本身证明已经操作。
5. T04 引用 P04 和 TASK/上游的确切版本，保留五章与检查/观察/反馈记录。设计约定及页面结构维护在 §2 或同版附件，快照绑定来源、实现与检查版本；派生检查输入标明唯一主记录。P04 不反向依赖 T04，避免循环。
6. 实际验证/豁免记录绑定 P04、T04 的当前版本及所观察的 HTML；两个条目可引用同一真实证据，但不能只给一项记录就说两项均有效。视觉评审报告同样说明对当前 HTML 的适用性；P04 不反向 refs T04。

共享 record 的三个结论严格区分：

| 结论 | 必需依据 | 不代表什么 |
| --- | --- | --- |
| I/V 内部检查通过 | 实际操作、来源核对及可定位检查记录 | 不代表真实用户已完成验证 |
| validation=verified | 真实目标用户、任务和观察；user_observation 证据，实际结论经人确认 | AI/子代理扮演用户不满足 |
| validation=waived | 已登记有权产品人的实际回复/评审、低风险理由与具体版本范围 | 不是已完成用户验证，也不覆盖新版本所有改动 |

没有真人记录或豁免时，可以不填写 validation，并在 T04/checkpoint 说明待验证；不要为了填字段制造 user_observation 证据。若记录 pending，依据应是实际当前状态/组织安排记录，不能伪造观察。缺必要验证时 gate 不应通过。

## 修订与接续

反馈更改业务规则时先更新 S2 并完成必要决定，再同步 S3 和 P04；更改功能先更新 S3，展示或未落实已定行为的问题可在 S4 修正。保留问题证据和影响范围，不直接把任何建议都增加为功能。

先更新对应设计记录和映射，按稳定区域/控件/状态定位实际改动及共享影响。优先局部修改并保留现有事件、数据和返回行为；必要重构写明理由、扩大的受影响任务和旧标识去向。结构检查后实际复验受影响任务及邻接路径；小改动仅补相应记录，不重新决定未受影响的设计。

更新 P04/T04 时用相同稳定 ID、实际 expected_version 和 change_reason；旧检查/视觉判决/观察不自动成为新版本批准。重走受影响任务，判断资料与四类结论的适用范围，conditions-go 仅按本轮固定条件进行一次修改完成核对，不新审；新范围/标准另立任务版本。需要补验或新豁免时保持待验证/待决定。完成后报告原型位置、版本和四类结论，不能仅写“测试通过”。
