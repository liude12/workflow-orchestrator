# S5 PRD 编写与需求评审

默认输出配套的《产品需求文档 PRD》和《软件需求规格 SRS》，随同一 T05 版本保存，另维护稳定 REQ/AC、追踪索引、R05/D05/Q05 及交付记录。先读[双文档结构与写法](references/prd-srs-writing.md)。前期可积累草案，正式定稿依当前范围的有效上游和实际评审。

新建或实质重生成 PRD、SRS 必须使用 `/ecc:plan-prd` 作为生成入口；执行前读[命令接入与双文档衔接](references/ecc-plan-prd.md)。先取得命令的 PRD 结果，再按有效上游展开 SRS。命令不可用时记未执行，已调用则据返回记失败或部分完成；准备输入但不绕过此要求生成，也不声称命令直接生成了 SRS。

## 进入与接续

先按[本轮任务范围](../../references/task-scope.md)处理局部试用或小修改；此时只读取适用要求，保留成果、来源和实际检查，不强制补齐整阶段登记。以下完整成果与交接要求用于正式阶段推进；小任务不能据此宣称阶段生效。

先读 [公共契约](../../references/contract.md) 与 [本地命令](../../references/local-tools.md)，独立调用也先 discover/resume。按 [项目定位规则](../../references/workspace-layout.md) 处理零个、唯一或多个项目；读取当前目标、本期范围、待决、影响记录及适用 S4→S5 交接决定。已有真实授权适用时直接引用。

核对 T01、T02、T03、P04、T04 及相关 SCN/RULE/FUN/PAGE/TASK 的确切有效版本与位置。历史批准或最新草稿不能冒充当前有效输入；无影响保留的历史引用必须有具体适用证据。必要用户验证未完成、规则未定或版本冲突时返回来源阶段，只整理不受影响的草案。

## 执行

按 [v1.1 阶段基线](references/baseline.md) 的 S5-A01—A08 推进：

1. 用 [R05/D05/Q05](assets/templates/r05-d05-q05.md) 逐项记录启动依据、有效性、版本冲突、命令入口可用性与阻塞范围。
2. 按[命令接入规范](references/ecc-plan-prd.md)实际使用 `/ecc:plan-prd`，保留执行及 PRD 输出记录；适用历史执行按规范复用。随后用 [追踪模板](assets/templates/requirements-traceability.md) 建立需求—场景—规则—功能—原型—验收关联，反查本期遗漏和无依据新增。
3. 用 [需求规格与验收模板](assets/templates/requirement-acceptance.md) 写清角色、入口、前提、输入、动作、响应、结果、状态、数据含义和可见/操作权限，补适用异常与边界。复杂跨系统、迁移、权限/权益、状态关联或必要首次详细规格展开时，读取并执行[能力约束与规格方法](../../methods/capability-specification/SKILL.md)，对照有效 PRD 与实际已有契约/系统材料区分业务约束、现状、实现建议和待决。简单清楚的范围不机械加做；发现的冲突及结果回同一 T05/SRS、REQ/AC 和 Q05。预期和阈值未知回来源阶段，不能用“处理正确”代替可判断结果。
4. 将第 2 步取得的 PRD 结果按 [PRD 模板](assets/templates/t05-prd.md) 整理为十一章业务需求，再依据该 PRD、第 3 步规格及有效上游按 [SRS 模板](assets/templates/srs.md) 写六章详细规格。逐项核对功能、通用约束、待决事项和验收的对应关系，引用唯一有效规则及其版本。
5. 先自检，再按 [评审处理模板](assets/templates/review-resolution.md) 整理产品、业务、研发、测试的真实意见。表达和引用自主修正；实质问题先回 S1/S2/S3/S4，落实有效决定后同步并复检，阻塞意见未关闭不算评审通过。
6. 正式交付前必读 [交付与受控文件规范](references/delivery-protocol.md)，核对 [交付清单](assets/templates/delivery-checklist.md)。材料和质量齐备后展示 manifest 版本、范围与哈希，只有实际有权人对该清单批准才 deliver；随后从实际导出目录检查链接、操作 HTML、打开图源，快照真实操作记录并用 delivery-check 登记结果。导出待检查与验收完成分别报告。

## 提交人工审核

按 [面向人工审核的写作规范](../../references/review-writing.md) 组织短摘要、业务正文与可回查依据。PRD 摘要先说明本期问题、用户能力、本次变化、重要规则和待决定事项，提供 SRS、系统布局及适用原型入口。产品经理与业务负责人先审 PRD 的目标、范围和验收，再按需进入 SRS 核对权限、状态、权益及异常后果。研发与测试从 SRS 查完整行为与可判定结果。

评审请求明确列出待决定事项、选项、建议依据、影响及实际责任人；不要把编号清单或笼统“请审核”当作请求。既有适用决定直接引用，无新事项不硬凑。评审摘要不扩大批准：正式交付仍呈现可查的确切文件版本清单，绑定其哈希和实际授权，且在正文、附件或检查变化后重新核对适用性。

等待评审时按[公共契约的等待规则](../../references/contract.md#等待评审与新增事项)保存具体基线和接续条件。新发现先判断是否影响当前承诺；后续增强留在候选记录，不持续追问新的业务取舍。实质问题仍按来源阶段修正和复核，不能因冻结基线而掩盖错误。

## 保存与门禁

REQ、AC、T05 用共享 put。REQ 引用实际功能/场景/规则/原型，AC 引用 REQ 与所用规则，T05 引用本期条目及适用上游，使用确切版本。将 PRD 作为 T05 正文，SRS 作为同版 review_bundle 中的 srs 文件，相关阅读附件按需登记。从登记版 PRD 打开 SRS，再核对返回入口和需求映射。[登记说明](../../references/registered-review.md)

双文档采用稳定的业务编号，并映射到真实 REQ/AC 版本。SRS 修订时同步检查 PRD、验收及本版评审，登记新的 T05 版本。R/D/Q 可作为可查附表。正文双向索引与工作区单向依赖分别维护。

方法采用按[专业方法接入规则](../../references/specialist-methods.md)记入现有 R05/Q05 或 T05 附件，不另建 PRODUCT.md 或替换十一章 PRD、六章 SRS。本地方法不能冒充 `/ecc:plan-prd` 的实际执行；命令不可用时只核查已有文档、整理事实和冲突，依赖命令的新生成仍未完成。

Q05-01—06 分别检查启动、追踪、规格、边界验收、真实评审和交付。T05 的 Q-V 必须有登记责任人的实际 human_review，另一代理自评不替代多角色评审；程序通过不能证明意见真实或覆盖充分。按 [质量与变更](../../references/quality-and-change.md) 保存修订和受影响复检，仅缺授权保持质量结论与待授权。

阶段生效、产品经理 handoff S5→delivery 和针对 manifest 的交付授权是不同记录，已有适用决定可复用。交付包检查失败须如实报告、记录阻塞并返修，不能因 deliver 返回成功就宣布交付验收通过；禁止手改导出快照补文件。每轮 checkpoint 写具体步骤、成果版本、等待事项和下一动作，最终报告说明实际交付位置、检查范围与限制。
