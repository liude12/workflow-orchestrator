# S5 交付与受控文件规范

配合 [本地命令](../../../references/local-tools.md)、[图表规范](../../../references/diagram-standard.md) 与 [S4 HTML 规范](../../prototype-design/references/html-prototype-standard.md)。本规范使用 put/evidence、gate/promote、manifest/deliver 和 delivery-check。交付是本地已授权快照，发布、上传或发送给别人须有对应任务授权。

## 1 在批准前准备可审阅清单

先读取 resume，核对目标、阶段适用性、有效成果与未关闭问题。执行或复用的阶段都要在 deliver.items 显式列出主成果，S1 为 T01，S2 为 T02，S3 为 T03，S4 为 P04 和 T04，S5 为 REQ、AC 和 T05。复用阶段同时列入计划指定的同目标、同阶段、有效版本。S2、S3 的登记版文档及原型操作证据须通过交接文件检查。已确认不适用的阶段记录依据及其对本次验收的影响。

交付表列条目 ID@版本、项目相对路径、正文/附件 SHA-256、适用范围、负责人、必要评审/决定及状态。双文档 T05 同时列出 PRD 和 SRS 的文件名称、产品基线与实际路径。先处理内容和可用性问题，再提交具体 manifest 授权。真实评审或验证尚有缺口时，记录其阻塞范围。

## 2 登记文件，不追着普通链接任意复制

双文档 T05 使用 review_bundle 登记 PRD 正文、一个 srs 文件及相关 support 文件。文件层级、相对链接和哈希随同一 T05 保存，SRS 进入 evidence 后随具体清单导出。从登记版 PRD 打开 SRS 并返回 PRD，核对版次、适用范围、章节及需求映射。[登记方法](../../../references/registered-review.md)

deliver 复制精确 refs 闭包中的正文，以及 evidence、检查、批准、validation、影响判定和本次授权所登记的文件。阅读资料的本地链接及资源须在批准前逐项登记。

批准前逐个检查阅读入口和必需资源。以所属正文文件为基准解析相对路径，确认在项目内、有确切版本且将被纳入交付。正文路径位于版本子目录时，不能把项目根相对路径直接当正文相对链接。绝对机器路径、file URL 或指回工作区的链接不构成交付可移植入口。

新 P04 在登记时已核对正文到命名入口/快照及本地资源的闭包，交付前仍复核同版路径和哈希。旧 P04 如正文链接命名 HTML、而 evidence 只有哈希快照，门禁会提示补齐新版本；选择适用的一种：
- 保留命名入口：在 P04 新版以 review_bundle 保存正文、该版本命名 HTML 和必要资源，记录所属版本和定位；已有 HTML 快照仍保留。T05 可继续附上同一原型的阅读别名及明确映射，但不能用 T05 附件掩盖仍断裂的 P04 正文入口。
- 使用已登记快照：在新的正文版本中把正式入口指向确实纳入包的快照，并核对从新正文目录到快照的相对路径。不要覆盖已确认正文。

draw.io 源、重要 SVG/PNG、原型必要本地资源采用同样方式。生成附件可用 evidence.kind=source 并在 locator 说明“版本化生成附件及所属对象”，这只是文件登记，不代表业务事实已核验；operation 只用于真实操作记录。所有文件先保留不可覆盖的版本/快照，登记时由工具计算哈希。禁止为补链接扫描复制整个工作区，或把未登记、越界及无关文件塞进交付目录。

静态检查 Markdown、HTML、CSS 和必要图表资源的本地引用；对片段锚点也核对存在。外部网址与本地文件分开列明，不能声称外部在线依赖已离线包含。原型优先自包含；已知缺资源、必要链接断裂或越界时先修复再授权。

## 3 先检查与生效，再绑定清单批准

完成 Q-I/Q-V、必要决定与真实评审，gate/promote 所有纳入条目。授权前将 Q05-06 的文件检查和待取得的授权分别标注。产品经理先确认 S5 可以交付。在 handoff.items 列出本期 T05 及其引用链未覆盖的其他本期 S5 交付条目，确保此决定覆盖本次 S5 范围。复核记录、适用计划、责任或版本发生变化时，查看 resume 返回的适用性与变更原因。确认或复用适用于当前范围的交接后，再由交付负责人批准具体包。导出索引同时保留两个决定与对应证据。

调用 `manifest --requirement 接收需求ID --items 条目ID…`，核对清单与文件映射，把 PRD、SRS 及其他成果的版本、范围、限制和 manifest.sha256 展示给实际有权人。即使全部复用外需求条目，此清单也涵盖接收需求的计划与角色。真实批准文件先 snapshot，再用该 evidence 与 approved_manifest_sha256 调用 deliver。最终批准归入 delivery.json，SRS 第 6 章链接交付准备和评审记录，导出后的实际编号在管理记录中回查。

如清单、引用、附件、检查、决定或上下文变化，重新生成 manifest 并判断原批准是否实际覆盖；脚本要求当前哈希一致。不能把旧批准文字简单复制成新批准，不猜测“应该同意”。只有已存在明确涵盖当前清单的真实授权可复用。

## 4 在实际导出目录验收

双文档交付先从实际包内 PRD 进入 SRS 并返回，核对 SRS 文件被列入 evidence、哈希一致且与 PRD 对应。逐条核对本期功能、质量要求和待决事项，验收记录定位到实际版本。旧单正文 T05 按原格式读取，再次采用双文档时从原工作稿登记新版本。

deliver 返回路径后，读取其中 delivery.json 的 manifest、精确版本 items 与授权证据，逐一核对被导出文件的哈希。检查报告保存在项目管理证据或交付记录旁的独立文件，记录实际包路径及 manifest 哈希；不要往已授权包内追加内容或修改快照。

至少：
1. 从导出包打开 T05，按清单打开实际纳入的 T02、T03、P04 等阅读入口。逐个解析必要本地链接、图片和 HTML 资源，确认目标位于包内且存在。
2. 对本次纳入的 HTML 原型，用当前可用浏览器从包内入口完成代表任务，记录路径、预期、实际结果和模拟标记。若原型阶段已确认不适用且本包没有原型，记录适用性决定及其范围。交付可用性检查与真人验证分别留证。
3. 对纳入的 draw.io 源按公共图表规范实际打开或用现有 CLI 读取验证节点/连接，核对正文编号；查看 SVG/PNG 可读、版本一致。已有图内容验证可复用，但仍要确认导出包内的源与图片可访问。工具不可用如实记未执行，不以扩展名存在冒充打开通过。
4. 对 REQ/AC、规则、评审及验证证据抽查关键定位是否可回查，确认没有无依据的新需求或错误版本。报告静态检查、实际打开/操作和未执行范围，不能把“文件存在”报告为任务已验证。

导出成功显示 exported（已导出，待包内检查）。AI 从 `resume.deliveries[*].required_checks` 取得本包必检入口，完成上述实际检查后快照日志，用 `delivery-check` 绑定交付编号、manifest 哈希和每个包内入口；原型条目附实际任务、预期、观察。字段见本地命令。工具核对文件及记录，无法认证观察真实性，不能用生成日志代替操作。

如任一必要检查失败，以 `delivery-check result=fail` 登记“已生成快照，交付验收未通过”，用 question/checkpoint 记录阻塞及受影响项，保留失败包供追溯。回到来源或本阶段修复新版本、必要复检，再生成新清单并核对真实授权后重新 deliver；禁止手改 delivery.json、登记哈希或补拷贝文件掩盖失败。全部必检入口有实际通过记录后才显示 delivered（交付验收完成），此状态不替代真人验证或实际业务批准。

## 5 完成报告

给出 T05/P04/验收的确切版本、导出目录、manifest 哈希、批准来源、已执行检查与证据、尚未关闭问题/限制和交接动作。没有真实批准或包内实测未完成时，分别标待授权/待交付检查，不宣称正式交付完成。此流程不要求无必要的新审批，已覆盖具体版本与范围的实际决定直接复用。
