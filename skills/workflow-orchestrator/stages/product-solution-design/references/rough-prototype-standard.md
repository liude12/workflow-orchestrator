# S3 可交互功能验证原型与功能覆盖规范

目的：把已整理的产品方案变成面向用户、可连续使用的产品系统，验证 S2 的本期场景、规则、状态和重要异常是否得到完整功能承接。采用接近 S4 展示质量、符合目标平台的入口、导航和业务页面，具体见[共享规范](../../../references/prototype-presentation.md)；几个孤立控件或功能演示不能代替本期产品原型。本阶段对外称“功能验证原型”，原“粗原型”目录和模板文件名保留兼容。

读取 T02 配套业务原型和实测记录，复用已验证业务路径及未解决问题。S2 验证业务是否走得通；本阶段验证用户通过产品功能和页面是否能完成业务。不能将 S2 的模拟控制台改名作为 S3 成果，或凭 S2 通过推断 S3 功能覆盖通过；界面若可复用仍须按本期 FUN/PAGE、布局和实际任务重新核验。

## 顺序与边界

1. A04 给出全系统初步页面布局，A06 落实关键取舍，先形成可审核的功能与布局方案。未确定的业务规则回 S2；不靠原型临时编一个规则使流程跑通。
2. 按这个方案生成功能验证原型；首次生成前写明输入 T03 草案及 FUN/PAGE、T02/SCN/RULE 的确切版本，以及平台、角色默认入口、导航、页面和同一对象的连续任务，复用 T03 布局记录。输入是方案基线，不冒充最终已批准成果。
3. 实际操作发现问题后，修正功能方案、布局及原型，再复检受影响任务。最终 T03 绑定同一版布局、HTML 和操作记录，不能交付互相矛盾的几份文件。
4. S4 优先复用这些成果中适用的界面、组件与已验证交互，再按正式要求细化视觉与交互、核验平台适配和开展真实用户验证。S3 内部功能检查不证明用户喜欢或理解方案，也不证明正式品牌、真实服务集成或生产性能已通过。

## 可交互功能验证原型的最低要求

- 交付可直接打开的自包含 HTML：样式、交互脚本、模拟数据和必要图形内置，不依赖 CDN、在线字体或未提供的本地文件。多个页面可在同一文件内由路由或视图切换呈现；页面清单中的每个本期页面应有对应视图。
- 默认打开起始角色的产品入口，使用目标平台适用的导航、内容组织和操作方式。模拟数据、演示样式、范围限制和评审工具在明确的外部评审条或独立说明中可查，不以教学说明和测试设置占据产品首屏。优先复用产品规范与组件；无正式品牌时 AI 选择统一演示样式，不提前要求 S4 品牌审批。
- 真实事件驱动关键行为：导航、点击、输入、校验、提交、反馈、业务对象状态变化、权限或状态拒绝、返回/取消。关键按钮不能无响应、只变颜色或一律提示“成功”；成功后的信息与可执行动作应随状态改变。
- 覆盖选定方案的全部本期功能和页面，核心任务从产品入口走到可观察结果再返回/接续，状态与输入沿途一致。小范围两页产品也应完整可用，不能为充页面擅加登录、消息、个人中心等业务或无效导航；必要能力缺失回到上游补方案。
- 测试角色切换、异常注入、负向操作和重置集中在独立评审入口，默认关闭；各角色业务操作在其产品界面完成，换角色不重置同一业务对象。拒绝路径须另外实际触发并观察，不靠隐藏按钮代替业务守卫验证。重要失败、输入不合法、无权限/状态禁止、空内容、处理中等按适用性提供触发方式。
- 人工或外部系统处理可用明示的模拟结果推进，但必须呈现交接、等待、失败与接续路径；记录谁负责真实执行。不向真实业务系统提交数据，不把模拟成功声称为依赖已验证。
- 尊重已确认的平台约束。未定平台/视口写为初步假设并标明影响；S3 操作过哪个环境就记录哪个环境，不能从单一桌面演示推断全部平台适配完成。

## 实际执行覆盖检查

使用 [功能验证原型与覆盖记录模板](../assets/templates/rough-prototype-and-coverage.md)。按以下顺序准备和执行：

1. 从有效 T02 提取本期核心场景、规则、状态转换和关键异常，不仅从已经实现的按钮反推测试；关联承担方及 FUN/PAGE。
2. 把每项变成可执行任务：明确角色、代表性输入及选择理由、初始状态、入口、逐步操作、预期反馈/结果和返回路径。按[共享规范](../../../references/prototype-presentation.md)在首次走查前约定任务产物的正确性、后续用途、适用领域约束和可观察使用负担；模拟能力与仍需真实验收的部分分开。每个核心场景至少有正常路径；相关重要规则要用允许与禁止的情形对照，关键异常和返回路径按适用性覆盖。
3. 在真实浏览器打开实际 HTML，先保持评审工具关闭，首轮覆盖默认入口及本期全部核心路径，完成任务、核对实际产物并返回/接续；多角色仅在切换身份时打开评审工具，各角色处理仍从产品页面进行。再用评审入口检查必要异常及负向动作。按共享规范的页面/视口计划查看各本期页面和关键状态，留存目标视口及适用窄屏的导航/溢出/滚动/触控与返回结果及截图；手机/小程序按手机优先设计，浏览器模拟不冒充原生或真机结论。静态解析、截图、单独调用业务函数及控制台事件通过，都不能替代用户路径实测。
4. 记录实际执行者/工具、时间、浏览器/视口、本次实测的 HTML 版本或登记哈希、操作步骤、预期与实际结果。截图或操作日志作为辅助证据，需对应具体任务；不能先填“通过”再补证据。
5. 每项结果只按事实写“通过／不通过／未测试／不适用”。未测试写缺什么环境或输入以及下一步；不适用说明规则与范围依据。核心任务没有实际操作证据时，S3 功能覆盖检查不能通过。
6. 从新增 FUN/PAGE、交互和依赖反查来源与本期范围，找无依据扩展和遗漏。明确人工或外部能力的模拟部分：原型能展示交接，不等于真实依赖已可用。
7. 对失败定位到 S1 范围、S2 规则或 S3 表达/实现问题，返回对应来源；修正后实际重新操作受影响任务，保留原失败记录和新结果。仅文档修正且不影响行为时说明判定依据。

工具不可用或原型无法运行时，可完成不依赖它的方案与检查准备，但原型任务保持未测试/阻塞。不得用“HTML 已生成”“源码完整”或“预计能走通”作为 Q03 通过依据。

## 保存与同版绑定

建议按需创建以下工作位置，名称按项目调整、历史文件保留：

```text
03-产品方案/
  页面布局/
    页面布局说明-v1.md
  粗原型/
    粗原型-v1.html
    粗原型说明与功能覆盖记录-v1.md
```

使用同一次 review_bundle 登记布局、HTML、实测记录和本地依赖。若布局就在 T03 §4，用 layout_heading 指明实际标题。独立布局文件标为 layout。需要独立留档的原始资料或批准可另行 snapshot。

这些是 T03 附件，不新增 P03 等类型，不占用 S4 的 P04。T03 refs 只指向已存在的上游及 FUN/PAGE 等确切版本；附件通过 evidence 绑定，不把 T03 与下属功能互相引用。HTML 或布局变化后分析哪些操作记录失效，修订并复检后登记新版本。

交付审核只需先看到：有多少页面、每页做什么、大致怎么排、从哪里打开、关键任务实际结果、还缺什么、下一阶段做什么。详细 ID、哈希、测试步骤和逐项覆盖放附录。内容检查、重要取舍的真实决定及 S3→S4 继续授权分别记录；复用仍适用的真实授权，不增加例行审批。

登记时按[可直接试用的审核材料](../../../references/registered-review.md)提交正文、原型、操作记录及实际依赖的资源。从 `put.path` 返回的版本正文点击入口，并在正式交接前复核同版文件。
