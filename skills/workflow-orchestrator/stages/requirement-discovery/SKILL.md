# S1 需求澄清

回答为什么做、为谁做、解决什么问题和本期做到哪里。成果是独立《竞品调研分析报告》、T01《需求定义书》和 R01/D01/Q01；产品探索属于本阶段，不另增阶段。

## 进入与接续

新需求启动或明确进入 S1 时，默认推进上述标准成果，先说明产出，不要求用户再次选择文档种类。用户明确限定局部任务时，按[本轮任务范围](../../references/task-scope.md)处理；此时只读取适用要求，保留成果、来源和实际检查，不强制补齐整阶段登记。以下完整成果与交接要求用于正式阶段推进；小任务不能据此宣称阶段生效。

先读 [公共契约](../../references/contract.md)、[本地命令](../../references/local-tools.md) 和 [面向人工审核的写作规范](../../references/review-writing.md)。独立调用同样先 discover/resume，读取当前有效版、最新草稿、来源、未决和 next_action；无项目先明确名称与位置，多项目请人选择。采用总控的同一状态，不另建项目记录系统。

只需一句想法即可开始。已有产品先保留未受影响的有效用户、目标和范围，聚焦变更；缺少信息可写有标记的草案，不要求用户预先补齐页面、流程和规则。纯文案润色直接处理，不启动调研或五阶段。

## 执行

合并多份既有规格时，从每项原需求的正文、验收条件和适用的补充决定提取可独立判断的业务结果，按 [R01 多来源合并对照](assets/templates/r01-d01-q01.md#多来源合并对照) 逐项核对去向，再从合并稿反查依据。T01 摘要说明实质差异和仍待确定的范围，附录指向这份对照。单一想法或普通需求澄清沿用下列步骤，无须建立合并对照。

新建整套系统或整体重构时，按[系统级需求分析](references/system-level-discovery.md)先梳理系统定位、业务域、角色协作、主要业务链、对象及能力依赖，区分整体范围与首期闭环。已有产品的局部修改复用有效整体定义，只检查受影响部分。不得把行业惯例当成企业已确认事实。

业务粗范围足以辨认实际服务，且涉及对外产品、平台分发或业务准入要求时，按[平台准入与资质核查](references/eligibility-check.md)判断适用性，优先实际读取平台及主管机关的现行官方依据，并把有依据的约束回填本期范围；结果为分析意见，不代表平台或主管机关审批。纯内部系统、无相关准入变化的局部修复按适用性裁剪，不额外要求空报告或重复提交材料；用户单独要求核查时只做该项。不能因无关或已明确的上线前置阻止独立需求及原型工作，影响首期方向的关键不确定性保持待核实。

形成或实质修订独立竞品报告时，读取并执行随包的[研究证据方法](../../methods/research-evidence/SKILL.md)；目标仍模糊或确需准备真实用户访谈时，选择其中相应部分。研究复核、目标诊断与访谈准备按任务分别触发，已有充分范围不重跑诊断。输入和结果沿用 RESEARCH/T01 与同一问题包，按[专业方法使用约定](../../references/specialist-methods.md)保留实际使用记录。

1. 读 [v1.1 阶段基线](references/baseline.md)，按 S1-A01—A08 的依赖和缺口执行，保留内部编号。先保存原件，再用业务语言整理“原话—谁在什么情境做什么—现在怎么办—卡在哪里—造成什么影响”。“加一个按钮”等原始提议先作为候选解法，不直接成为已确认需求。合并同一问题的重复描述，仍保留各来源；不同人的冲突诉求并列，不悄悄取舍。
2. 提问前通读已提供及已授权可用资料、适用的历史回复，按“已知、未知、冲突、可后置”盘点，先自行补查、同题去重，保留冲突双方来源。用 [信息缺口与集中补问模板](assets/templates/information-gaps-and-questions.md) 一次整理当前可识别的完整高价值问题包，按主题分组并突出阻塞项，不按 3—5 题人为拆成多轮。每题写清已知、具体缺口、影响和应由谁回复；可用自然语言批量回答或写“不知道”，条件题一并给出适用分支。仅核实会影响本期方向的规则、平台及既有视觉条件，不在 S1 预定 S2—S4 的详细方案。资料充分不凑问题；非阻塞细节交后续阶段。
3. 新产品、新增、优化和重构默认实际开展竞品与市场调研，读取 [调研方法与存储约定](references/research-and-storage.md)。先把本期关键不确定性变成具体调研问题，再搜索并打开来源；不凭记忆编写已验证结论。数量按复杂度和证据质量调整，不以产品名称或功能清单凑通过。
   当实际截图、官方演示或用户提供的材料有助于理解产品时，按[可查看的竞品材料](references/visual-research.md)组织带来源和局限的阅读入口，可按需使用[HTML 模板](assets/templates/competitor-view.html)。明确区分实际操作与官方材料；未取得、未操作或受权限限制的部分如实说明，不造截图、视频或二维码，不以静态检查代替浏览器验证。已有适用阅读入口时直接复用，不强制新增文件。
4. 从问题形成目标、范围、非范围、约束和验证方式，解释每项范围解决哪个问题、现在为何需要做。区分已确认事实、分析判断、建议与待核实；竞品规则不能成为本产品的已确认规则。缺少频率、影响规模或指标基线时保持未知，不编数字来突出价值。
5. 将需人处理的事项写成可回答的决策问题，给出实际候选及其差异、推荐依据、影响与责任人，并入同一问题包，不另发重复问卷。收到回复后回填已回答项并复用其适用范围；只有新回复或新增材料引入新缺口、冲突时才针对相关未解决项补问，不重复已答问题。未答或“不知道”保持待核实，不视为同意、不编默认规则；只暂停受影响部分，继续独立分析。没有待拍板事项就明确写无，不机械索取确认。
6. 用 [竞品报告模板](assets/templates/competitor-report.md)、[T01 模板](assets/templates/t01-requirements.md) 和 [R01/D01/Q01 模板](assets/templates/r01-d01-q01.md) 保存草案。报告和 T01 先写审核摘要，再写业务正文，证据及编号详表放末尾；首屏让产品经理与业务负责人看到结论、本期边界、重要未知和需要自己回复的事项。T01 保留独立报告的确切版本、结论编号与支持来源引用，不能只写“已参考竞品”。

## 保存、检查与交接

正文使用共享脚本 put：新项目中 RESEARCH 保存到 `01-需求澄清/竞品调研/<ID>/v<N>.md`，T01 到 `01-需求澄清/需求定义/<ID>/v<N>.md`；已有英文项目沿用原布局，以脚本返回路径为准。refs 建立来源 → 报告 → T01 关系。RESEARCH 只是独立报告的实现类别，不替代 T01 或 R01/D01/Q01 编号。AI 维护索引和版本，用户无需编辑 JSON。原件、已确认正文和证据快照不覆盖；变更按 [质量与变更](../../references/quality-and-change.md) 分析下游影响。

按基线 Q01-01—06 检查依据、问题、目标、范围、决定和交接。检查摘要能否独立说明核心问题、价值、边界与待决，是否与正文一致；用来源核对其没有把建议压缩成事实或把重要限制藏到附录。Q-I 是内部检查；Q-V 的 T01 目标范围与重要事实需要实际责任人核验，不能用自读草稿替代。搜索失败、需登录/付费和未获取的交互均如实标记未验证；缺必要证据保留草案。

阶段结束先展示业务结论、相对上一版的实质变化、需负责人回复的具体事项，再给报告与 T01 的阅读入口、版本、检查依据及 S2 接续建议。明确业务负责人核实哪些事实、产品经理决定哪些目标和范围，不把“请审核”作为唯一请求。质量通过但缺批准时保持待授权；确认某条范围不扩展为全部批准，gate/promote 不等于同意进入 S2。实际产品经理的继续决定由 handoff 绑定版本；先 checkpoint 保留下一步，再交回总控或等待决定。
