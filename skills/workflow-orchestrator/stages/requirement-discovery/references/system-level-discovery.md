# 系统级需求分析

本方法补充 S1-A02—A07，适用于新建整套产品、整体重构或需要重新确认系统职责的任务。目标是让 T01 说明系统如何承接业务，并据此划分首期。局部优化只检查相关整体定义及影响，不强制重做本方法。方法讨论、Skill 检查等请求不创建业务项目。以下是 AI 分析与检查要求；正文按[公共写作规范](../../../references/review-writing.md)用业务语言表达，追踪和执行记录单独保存，不把本方法整份变成用户问卷。

## 先明确分析对象

依据用户原始要求、已有项目和有效定义说明本次分析对象及依据。系统名称不能直接证明经营模式、角色、业务域或范围；用户只给一句想法时，可以提出整体草案和候选，不补造企业现状。

系统级任务同时维护：

- 整体业务范围：系统长期准备服务哪些组织/用户、承接哪些任务与结果；候选和已确认分开，不承诺无依据的建设周期。
- 本期范围：本轮选择实现的业务闭环、依赖、排除项和暂由人工/外部承接的部分，以及取舍依据。不能用“首期只做一个功能”代替整体分析。

已有整体定义适用时引用其确切版本，只补缺口与变化。整体重构先区分需要保留的业务事实、现有问题和建议的新机制；不把所有现有功能自动保留，也不自动推翻它们。

## 从业务组织分析，避免从菜单拼系统

按以下关系整理已有事实、假设与缺口，信息充分时可合并表达；表格或清晰文字即可，不强制每项画图或另建文档。

| 要形成的认识 | S1 需要说明的内容 | 用什么判断是否足够 |
| --- | --- | --- |
| 定位与建设目标 | 服务的组织/业务模式、主要用户、建设原因、预期业务结果、系统职责及重要约束 | 能解释为什么需要该系统，事实与候选定位可区分 |
| 业务域与系统边界 | 主要业务领域，本系统负责的事项，人工/其他系统负责的事项及衔接 | 每个主要结果有承担方；涉及的业务域有来源或标为待核实，不按行业常见模块默认纳入 |
| 角色与协作 | 使用者、运营/管理者及必要外部参与方的任务和交接关系 | 关键环节有角色承接，角色的困难分别说明；未确认职责保持未知 |
| 主要业务链 | 从触发到结果的业务环节、角色交接、关键输入/输出，以及会改变范围的重要分支 | 能跟随一个代表性业务从头走到结果，缺失环节、外部承接和假设明确 |
| 业务对象概览 | 业务围绕哪些对象运作，对象含义、关联及在哪些环节产生、使用或结束 | 跨角色/业务域引用的对象含义一致；不要求字段、数据库表或完整状态机 |
| 能力及依赖 | 支撑业务环节的候选系统能力，服务角色/问题/目标、依赖和本系统/外部责任 | 能说明能力为什么存在、怎样共同支撑业务结果；尚不确定页面与按钮 |
| 分期与验证 | 整体能力与首期的对应、闭环切分理由、排除的承接方式、验证目标的方法 | 首期能产生所选业务结果；有依赖但暂不建设的能力有明确承接或待决 |

将问题、目标、业务环节、对象和候选能力相互关联，编号采用文档内稳定标识即可，不新增 put 类型。继承公共来源约定；相关判断引用真实项目资料、调研结论或实际决定，AI 补充保持推断/建议状态。

## 集中澄清并按依赖收敛

提问前读取已有资料、有效决定与历史答复，先自行补查并合并同义问题。把当前可识别的关键缺口一次按主题集中提出，写明已知、具体缺口、影响、候选和需要谁回复；条件问题一并说明适用分支。不要要求用户填写全部角色、规则和模块清单，也不人为把已能识别的问题拆成多轮。

问题可按服务对象与目标、业务链与交接、能力边界和首期取舍分组；这是阅读组织，不是固定问卷。资料充分直接整理；仅新答复或新增资料引出真正无法预见的依赖、冲突时，再针对未解决内容补问。细节交后续阶段，等待时继续独立分析。收到回复后回填原答来源、实际结论和受影响章节，不能只在文末追加问答或把建议记为批准。

不要只为覆盖商业租赁、多组织等行业可能性，就要求用户重选已有输入已支持的经营情境。先说明有依据的工作理解；重要前提确实仍会改变当前职责/范围时，再提出具体确认。职责问题问谁承担业务结果，不把工具中的角色登记、实际姓名或阶段许可清单混入需求正文。

当关键业务链、目标用户或内外部职责仍可能改变整体方向及首期范围时，继续保留系统级草案与阻塞问题；不能以章节齐全宣告定义完成。重要事实、目标范围仍由实际责任人核实/决定，沿用 Q-V、approval 和 handoff。

## 调研支撑整体判断

以定位和主要业务链组织调研，选择可比产品或替代方案，比较角色覆盖、业务衔接、能力边界及其前提。只有一个页面/局部功能的证据时，限定结论，不能据此宣称已了解整套系统。竞品有某业务域不说明本系统需要该业务域；候选借鉴要能关联本产品问题/目标，再由有权人取舍。检索、证据和报告版本沿用 research-and-storage.md。

## 交给 S2 的边界与检查

本阶段识别主要业务、对象、能力及会改变方向的重要约束，S2 在已选范围中展开详细场景、职责、规则、状态与异常；S3 再确定产品功能与页面。不要提前虚构所有业务细则，也不要把定义系统职责所必需的问题推迟到 S2。

使用 Q01 原有六项记录实际内容检查：

- 覆盖：从来源反查主要角色、业务域和任务是否遗漏，不能只围绕首个功能展开。
- 贯通：选一个代表性业务从触发到结果，核对环节、交接、对象和能力，断点有承接或明确缺口。这里只是分析推演，不冒称用户验证。
- 边界：整体范围与首期分开，能力能对应问题/目标；未纳入部分有理由，首期依赖有承接。
- 一致：角色、对象、目标、范围表与场景相互对应；变更后逐处回填，来源/报告版本可追溯。
- 就绪：没有会改变本期方向或边界的未关闭阻塞项；其他待决有责任/下一步，实际批准和继续决定可回查。

已有项目沿用有效模板时按实际缺口补充上述认识，不为采用新模板无条件重写已确认正文。

## 粗范围后的准入核查

主要业务能力足以辨认实际服务后，先按[平台准入与资质核查](eligibility-check.md)查影响定位、主体和首期的条件，再收敛首期。不要等所有页面、状态或 PRD 写完；初步分析和查可用来源可以并行。核查后的约束回填本期边界和职责；已明确的上线前置保留安排，关键可行性未知保留条件草案。
