# 竞品调研方法与版本引用

## 何时执行与如何裁剪

新产品探索、功能新增、优化、重构默认开展竞品与市场调研；已有有效报告可复用适用结论，同时实际核查本次变化有关的来源和时间。说明复用范围与新增核查，不把“已有报告”当完全跳过调研的理由。仅无业务变化的普通文案任务不启动 S1；用户明确限制联网时遵从，记录本轮调研限制与仍需补证内容，不能写已完成外部核查。

数量随问题复杂度与证据覆盖调整：简单需求通常 2—3 个，中等 3—5 个，复杂业务或新产品通常 5 个及以上按需扩展。这是选样参考，不能将 5 个名称当完成标准。记录候选数、实际获得证据数、选择依据、覆盖盲区；证据不足时扩大候选或缩小结论范围，不编造竞品和功能。

先定义调研问题：本产品服务谁、要解决什么任务、当前关键不确定性是什么。按任务、用户、业务模式或渠道选择直接竞品，必要时加入替代方案并说明可比性。对局部变更聚焦相关能力和流程，不重复做无关全景扫描。

选样后用“本期关键任务 × 参考对象”核对覆盖。每个对象明确平台/渠道与本次实际观察的版本或日期；不同平台能力不能互相代填。比较写到用户能做的动作、输入/条件、调整或选择、输出信息和后续使用；不以“支持生成、支持社区”等模块名称代替。缺失、未验证和不适用分别标记，不能空白或推断为不支持。附候选纳入/排除依据和代表性：哪些任务/渠道已有证据，哪些仍是盲区。只有三个样本也可支持限定结论；数量更多但遗漏关键任务仍不合格。

调研前先整理用户已有资料能支持的现状与问题，避免把竞品功能清单当需求清单。将不确定性写成“这条发现会改变什么目标或范围判断”的具体问题；公开资料无法核实本企业事实时保留人工核实项，不拿外部相似案例代答。

## 实际搜索、打开与证据

1. 使用当前可用的搜索/网页读取工具，不新增搜索脚本、服务或专用 MCP。以产品类别、用户任务、候选名称和具体能力组织查询，保留实际查询词与时间。
2. 优先官网、帮助中心、官方公开介绍与可访问页面。可信用户评价作为“第三方评价”单列，注明作者/渠道、时间、样本局限；不把个体体验提升为普遍事实。
3. 搜索后打开具体来源页，核对它是否直接支持本次论断。仅看到搜索摘要时注明“仅检索线索，未打开核验”，不能称已验证功能或流程。页面无该信息不等于产品没有该功能。
4. 保存检索/读取记录：工具、查询、来源标题、直接 URL、访问时间、发布日期或版本（若提供）、定位段落/小节、支持的论断和访问结果。原文摘录只取支持结论所需的短片段，遵守工具的引用限制；其余用准确摘要。保留真实执行记录，不自制“已搜索”日志替代工具调用。
5. 登录、付费、地区限制、403、搜索失败、失效链接和只得到二手描述，按实际结果写“未验证”或局限。仅有营销介绍时不能声称操作过后台。交互方式只在获得相应页面/视频/实际操作证据时描述，标明获取方式；没有就写未获取。
6. 工具不可用时交付已知部分与待验证清单，说明实际尝试、缺口影响和补证动作。不能造出成功检索、URL、评论或用户体验。未完成必要调研的报告保留草稿，依赖其未验证结论的 T01 不生效。

时间使用用户所在时区，记录日期或可获得的精确时间；不要给未提供发布日期的页面编日期。动态功能、套餐、规则的结论注明适用日期。

## 四类论断与结论

每个重要论断分配报告内稳定编号（例如 F01 事实、V01 第三方评价、A01 分析、P01 建议），并有对应来源或推理依据。编号是报告内定位，不是新的业务阶段编号。

| 类型 | 应写什么 | 不应混入 |
| --- | --- | --- |
| 客观事实 | 已打开来源直接支持的定位、功能、流程或规则，注明适用对象/日期和局限 | 尚未访问的功能和本产品事实 |
| 第三方评价 | 谁在何时何渠道如何评价，样本与偏差限制 | 普遍用户结论或官方承诺 |
| AI 分析 | 基于哪些事实/评价比较差异、推导意义，说明推断条件 | 未核实的因果、收益和市场份额 |
| 建议 | 可借鉴点、适用前提、不适用点、当前需求启发及需要人决定的取舍 | 已确认的本产品规则或范围 |

“竞品允许提前 24 小时取消”即使有来源，也不能直接写成本产品规则。先说明它服务的业务假设，再交有权人确认本产品取舍；无决定时保留候选。

## 独立报告与 T01 的关系

按 [报告模板](../assets/templates/competitor-report.md) 输出可单独阅读的《竞品调研分析报告》，包括定位、来源链接、调研时间、证据、任务问题、功能流程、交互（可获取时）、差异、借鉴与不适用点、对当前需求的启发及限制。

给产品经理与业务负责人的报告按 [面向人工审核的写作规范](../../../references/review-writing.md) 编排：结论与本期建议在前，关键差异和取舍居中，来源、论断编号及执行记录在附录。正文在关键事实旁保留简短来源和信息状态，足以改变建议的证据缺口放入摘要；移动来源表不等于降低证据标准。

T01 只提取与本期相关的关键结论，并逐条记录报告 ID@版本、结论编号、原始来源、影响的目标/范围、建议/已确认/未采用状态及决定依据。这样报告不是 T01 中几句无来源的背景，T01 也不复制维护另一份完整报告。

证据不足不等同于产品不存在；数量低于参考不必虚构补齐。若已获得的来源足以支持明确限定的结论，可以交付有局限的报告，但要在 Q01 说明缺失维度及其不影响本期判断的依据。缺失内容会改变方向或关键范围时仍为阻塞。搜索完全无法执行时不得宣称默认外部调研已完成。

Q01-01 逐项反查比较表的证据、平台和操作细节；Q01-04 判断候选代表性及覆盖是否足以支撑本期建议。关键任务缺证据且会改变建议时不通过：扩大检索、补观察或明确缩小建议范围后复检。不能仅凭字段齐全、链接可开或竞品数量宣布调研充分。

## 共享脚本登记顺序

以下为文件与版本约定，具体命令字段见 [本地命令](../../../references/local-tools.md)。不要直接改 state.json。

1. 保存用户原始输入及真实检索/页面读取证据到工作文件，再用 snapshot 保存不可变副本。用 SRC 条目登记它们，证据 locator 指明实际原话/网页小节/操作记录。SRC 表示实际来源记录，不是 AI 报告的替身。
2. 写报告工作稿，然后 `put` 为 `type:"RESEARCH"`，标题《竞品调研分析报告》，refs 指向所用 SRC 的确切版本。RESEARCH 属于 S1，不新增业务阶段，不替代 T01 或 R/D/Q。
3. 脚本返回稳定 ID 和路径，新项目例如 `01-需求澄清/竞品调研/DEMO-RESEARCH-001/v1.md`；已有英文项目沿用原布局。以返回值为准，报告内结论编号保持稳定；不按文件名猜当前有效版。
4. 写 T01 工作稿，正文给出相对链接和报告 ID@版本/结论编号；put 为 `type:"T01"`，refs 包含报告版本和实际使用的原始项目来源/问题版本。没有报告时先写草案与缺口，不伪造 RESEARCH 引用。
5. 报告与 SRC 的 Q-I/Q-V 用真实来源交叉核查或实际执行证据；报告的分析透明性可以被复核，但本产品真实事实和目标范围批准仍由人承担。T01 按共享门禁记录责任人的 human_review 和 product 决定。
6. 报告更新使用同 ID、当前 expected_version 和具体 change_reason，脚本生成 v2 并保留 v1。T01 会进入影响候选；审查结论变化后修订 T01 或记录有证据的无影响判断。未排除影响时不能用历史批准版本作为当前有效输入。

登记报告的 payload 形状（替换为本项目实际路径与已存在 ID，不可原样作为证据）：

```json
{
  "requirement": "DEMO",
  "type": "RESEARCH",
  "title": "竞品调研分析报告",
  "body_file": "报告工作稿的实际绝对路径",
  "expected_version": 0,
  "refs": [{"id": "DEMO-SRC-002", "version": 1}],
  "decision_roles": []
}
```

T01 的 refs 示例：`[{"id":"DEMO-SRC-001","version":1},{"id":"DEMO-RESEARCH-001","version":1}]`。此示例只是结构，不证明任何来源真实或已验证。

## 集中待决与阶段结束

待决记录用 [R01/D01/Q01 模板](../assets/templates/r01-d01-q01.md)，面向人工的请求写入 T01 的决定卡。先区分事实核实、目标范围决定和后续业务规则问题，给出依据、候选、推荐原因、影响、阻塞性与责任人；不要逐条催问或把已回答事项重问。已有主记录直接引用，不能因新加摘要而生成另一套决定。

向用户呈现报告/T01 的实际位置、版本、检查与缺口；重要事实或范围无批准时保留草案或待授权。真实产品经理的阶段继续决定绑定本次具体版本，才能 handoff 至 S2。checkpoint 写清当前 A 步骤、已尝试补查、待谁决定和可继续的独立工作。
