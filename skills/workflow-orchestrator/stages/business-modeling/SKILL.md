# S2 业务建模

回答由谁、在什么条件下、处理什么、产生什么结果，以及异常时如何继续、恢复或结束。输出 T02《业务模型说明书》、可交互业务验证原型及操作记录、适用图表和 R02/D02/Q02。原型用于检验业务模型，关键规则仍由真实业务负责人决定。

## 进入与接续

先按[本轮任务范围](../../references/task-scope.md)处理局部试用或小修改；此时只读取适用要求，保留成果、来源和实际检查，不强制补齐整阶段登记。以下完整成果与交接要求用于正式阶段推进；小任务不能据此宣称阶段生效。

先读 [公共契约](../../references/contract.md) 与 [本地命令](../../references/local-tools.md)，独立调用也先 discover/resume。核对 T01 的确切有效版本、来源、范围与 S1→S2 适用交接决定；可复用已明确的实际授权，不重复询问。原件先 snapshot，不另造状态系统。

范围改变回 S1。T01 缺失/失效或未取得必要交接时，可整理不依赖缺口的候选模型，明确其草稿状态；不伪造有效输入。已有产品聚焦变化和关联影响，复用仍有效的场景与规则。

## 执行

读取 [v1.1 阶段基线](references/baseline.md)，按 S2-A01—A08 的依赖与缺口工作：

专业方法按[接入约定](../../references/specialist-methods.md)在本阶段内执行。跨角色、多对象或重要异常较复杂时，用[场景覆盖方法](../../methods/scenario-coverage/SKILL.md)准备或独立查漏；已有用例覆盖的小改动只复验受影响项，业务规则仍由本阶段确定。

1. 从本期范围列核心场景，明确触发、参与者、业务对象和结果；区分现行业务事实与拟建机制。
2. 定义发起、处理、审批、接收与维护责任及对象含义。从触发走通正常流程，多角色交接标明交付物与承接者；角色对象不是数据库表或页面。
3. 补条件、规则、状态与适用异常。多条件组合用决策表，有生命周期才展开状态模型；检查失败、取消、超时、重复、冲突、交接中断及跨业务权益/资源影响。
4. 未知规则写候选、依据、影响和待决，集中交业务负责人；行业惯例和竞品做法不能补成本企业已确认规则。决定后将同一 RULE@版本同步到流程、状态和异常，再推演。
5. 用 [T02 模板](assets/templates/t02-business-model.md) 与 [业务分析记录模板](assets/templates/scenarios-rules-states.md) 成文，按 [推演与 R02/D02/Q02 模板](assets/templates/r02-d02-q02.md) 核验正常、分支和重要异常。
6. A07 读取并执行[原型生成适配方法](../../methods/prototype-build/SKILL.md)的 S2 适用部分，按 [业务验证原型规范](references/business-prototype-standard.md) 结合[共享展示规范](../../references/prototype-presentation.md)，先明确目标平台、角色入口和场景页面假设，再生成接近 S4 展示质量的可操作 HTML；增量修改只处理受影响范围。默认在用户界面完成业务，角色切换、故障、资源快照与记录从独立评审入口打开。按 [原型与覆盖记录模板](assets/templates/business-prototype-and-coverage.md) 在真实浏览器分别实测用户正常路径与评审模式的关键分支、异常、角色限制及恢复；发现问题先回填同一业务模型，再同步原型复检。未知规则的相关操作显示待决定并保留原业务状态，不默认采用候选；独立已明确路径可继续验证。
   对跨角色、跨入口的核心路径，在同一次演练中沿同一业务对象切换经办人和入口，核对原件、下游事项、回执与业务规定的终点。只有分段证据时，指出尚未接上的那一段。

## 给产品经理和业务负责人审核

编写前读取 [面向人工审核的写作规范](../../references/review-writing.md)。T02 先给审核摘要：业务怎样运转、关键变化、重要规则的确认状态，以及具体需要核实或选择的事项。先用一个完整业务案例串起角色、动作和结果，再展开流程、规则、状态与异常；不让审核人先解读编号表。

摘要提供原型入口和复现步骤，分列实测通过、有缺陷、待决定和未测的核心路径。对每个重要断点写明哪件事到谁手中、最后观察到什么、缺哪一步，以及由谁补证或决定。S3 据此设计产品功能与页面；S2 的角色开关和模拟事件只服务于演练。

正文使用业务名称和短表；复杂决定用记录卡解释候选、依据、影响和期望回复。ID、精确版本、证据定位和逐项检查放追溯附录，正文仍就近标明未知/建议/已确认。无新增待决就说明，无须让人重复批准已有适用决定。交付前检查：不翻附录能否看懂主要流程、关键规则和这次要决定什么；把同一个案例按正常和重要异常走完，避免只在旧模板前加摘要而正文仍不可读。

## 图表、保存与交接

图表遵循 [公共 draw.io 规范](../../references/diagram-standard.md)。保留可编辑源文件，重要图导出 SVG/PNG；节点编号、规则版本、图文一致。实际重新打开、检查连接、导出并查看图像才算工具验证；只生成 XML 或阅读代码不算。可从 [最小泳道模板](assets/templates/business-flow.drawio) 起步，但必须替换 TEMPLATE 内容及说明，不能把占位图当业务成果。

SCN/RULE 通过共享 put 保存，T02 按[审核材料登记规范](../../references/registered-review.md)使用 review_bundle 提交，以 put 返回的 path 打开版本正文；按需创建 `02-业务建模/业务原型/` 保存版本化 HTML、说明与实测记录。已有英文项目沿用原布局，以脚本返回路径为准。refs 指向实际采用的 T01、来源、场景与规则版本，不引用 T02 自身或尚未形成的 FUN/PAGE。图源、导出图、原型、说明与实测记录随本次 review_bundle 登记，保持相对链接可用；不新增 P02 类型，也不占用 S4 P04。R02/D02/Q02 可作附表。

登记 T02 的 I 类通过检查时，按[本地命令中的 T02 登记说明](../../references/local-tools.md)引用本版实际闭环证据。检查人核对每个结论对应的操作和终点，命令返回值只按该命令实际校验的内容解释。

按基线 Q02-01—06 记录真实检查，包含 SCN/RULE/流程节点到原型操作和可观察结果的覆盖。源码、截图和文字推演不能代替浏览器操作；无法运行写未测试，不得报通过。展示检查并入 Q02，按共享规范记录默认用户入口、连续任务、独立评审、层级/反馈和适用视口；控制台事件通过不能替代用户路径通过。缺品牌材料时由 AI 形成有标记的统一演示样式；图表验证仍按原要求独立完成。AI 推演与原型内部操作不能代替 RULE/T02 的真实责任人核验、决定或真人观察。只有质量、决定和版本适用时 gate/promote；仅缺批准保留待授权。展示 T02、原型入口、实测证据、未关闭问题与 S3 接续建议，由产品经理确认继续，再记录 handoff S2→S3。每轮 checkpoint 到具体 A 步骤，缺失规则只阻塞受影响部分。
