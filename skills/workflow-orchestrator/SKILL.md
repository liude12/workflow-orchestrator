# 产品团队 AI 协作工作流

首次进入读取[公共执行契约](references/contract.md)，根据用户请求、已有资料和项目状态，按[本轮任务范围](references/task-scope.md)确定执行范围，再用[项目定位规范](references/workspace-layout.md)接续。新需求启动默认按 S1 标准成果推进，无需用户重新选择产出。命令及输入见[本地维护工具](references/local-tools.md)，状态与编号见[成果数据规范](references/artifact-schema.md)。局部修改不机械初始化五阶段或逐页登记；以下完整流程用于推进阶段成果。

## 项目定位与接续

1. 优先使用用户明确指定的项目路径；否则在当前工作目录有限范围运行 discover。唯一项目读取 resume；零项目先明确产品名称与保存位置；多个候选展示路径和项目名让用户选择。不能根据目录名猜状态，不能擅自批量初始化。
2. 读取原始资料、当前有效成果、候选版本、待决、交接记录和 next_action。新资料先 snapshot 保存原件。不得以聊天摘要代替项目文件。
3. 根据变化来源选择阶段，复用适用的已确认成果：目标范围 S1，业务规则 S2，功能行为 S3，交互展示 S4，PRD 表达和验收 S5。五阶段保留适用性与依据；不强制重做全部方法。
4. 调用表示按需读取对应 SKILL.md 并执行其工作，不假定存在同名平台函数。阶段独立进入也遵循公共规范。

| 阶段 | 入口 | 主要成果 |
|---|---|---|
| S1 需求澄清 | [requirement-discovery](stages/requirement-discovery/SKILL.md) | 资料缺口与统一问题单、独立竞品报告、T01、R01/D01/Q01 |
| S2 业务建模 | [business-modeling](stages/business-modeling/SKILL.md) | T02、规则/流程/状态、可交互业务验证原型及实测记录 |
| S3 产品方案设计 | [product-solution-design](stages/product-solution-design/SKILL.md) | T03、系统页面布局、可交互功能验证原型及 S2 覆盖验证 |
| S4 原型设计与用户验证 | [prototype-design](stages/prototype-design/SKILL.md) | 可选 UI/UX 资料与设计依据核验、P04、独立视觉评审、T04、Q04、真实验证或有效豁免 |
| S5 PRD 编写与需求评审 | [prd-authoring-and-review](stages/prd-authoring-and-review/SKILL.md) | 经 `/ecc:plan-prd` 生成入口形成配套 PRD 与 SRS，同版 T05、验收、评审与交付记录 |

## 执行与交接

- 进入适用分析或生成任务时，按[专业方法接入规范](references/specialist-methods.md)读取并执行随包的适配方法：S1 研究与访谈、S3 任务组织、S2—S5 用例查漏、S2—S4 原型生成及 S5 复杂规格核对。阶段仍负责有效依据与检查，方法结果回填原有成果；小改动按影响裁剪。可选外部插件按实际入口使用，不能把方法执行记成原命令调用。
- 每个实际进入的阶段，在成果可阅读或遇到影响当前工作的关键缺口时，按[阶段反馈](references/contract.md#阶段反馈)说明实际进展、阅读或试用入口、确需人决定的事项和下一步；反馈合并到当轮对话，不为汇报停下已授权且不受阻的工作。
- AI 自主分析、生成、自检和修正。集中提交需人处理的事实、规则、范围和取舍，附原因、候选、推荐依据、影响、阻塞性、责任人及已有决定；等待时继续独立部分，未回复不是同意。
- 以用户本轮任务安排执行；已明确授权的准备、修改和内部检查连续完成，不逐文件请求“继续”。阶段交接和具体交付授权仍按实际范围核对；在一轮回复中说明具体待决定事项，不把 AI 能查证、设计或修复的工作交给用户填写。
- S1 先盘点已知、缺失、冲突与可后置项，将当前可识别的关键问题按主题统一提出，复用已答信息。新建系统先分析整体业务关系和首期边界；涉及平台或业务准入时按 S1 核查适用的现行官方依据。S2 用业务验证原型检验角色、流程、规则、状态与异常；S3 用页面与功能验证原型检验产品承接。两阶段均按[原型展示规范](references/prototype-presentation.md)默认呈现面向用户的产品入口、页面与连续任务，展示质量接近 S4，评审工具独立打开；阶段职责和验证证据不变。S4-A01 的用户 UI/UX 资料可选：已有则复用，没有可暂不添加，由 AI 根据有效 S3 形成具体暂定设计约定后继续，不为常规选择追加批准；明确的品牌强制要求、规范冲突和上游缺口仍按实际影响处理。设计依据就绪后开发并进行独立成品评审。
- 用维护脚本管理快照、条目与版本。最新草稿不是当前有效版。上游变化按[质量与变更](references/quality-and-change.md)分析影响；失效或待分析内容不能用于正式交接。
- 合并既有规格时，S1 按原文逐个核对可独立验收的结果。S2 从原文和有效决定选定关键路径及终点，再沿同一笔业务跨入口、换角色实走。按[本地命令](references/local-tools.md)以具体操作证据登记 T02 内部检查。
- gate 只证明记录及文件约束满足，不证明业务真实。内容通过、必要决定和验证齐全后 promote。阶段完成再展示成果位置、版本、检查依据、未关闭问题和接续建议，由产品经理确认交接，记录 handoff。不要将条目有效误当成同意进入下一阶段。
- 已有决定或交接确认适用于本次对象、版本和范围时直接复用，不重复询问。仅缺授权保持待授权，不重写已通过内容。
- S2、S3 交接前，从 put 返回的登记版正文实际打开并操作同版原型，核对实测记录，S3 另核对系统布局。文件清单与旧项目补齐方法见[审核材料登记规范](references/registered-review.md)。S5 先核对本期各适用阶段主成果，再分别核对产品经理的交接决定和交付负责人对当前清单的批准。
- 每轮实质工作 checkpoint 到具体子步骤与下一动作。恢复先读取文件；写锁或损坏时保留证据，不擅自清锁或补造批准。

## 输出与适配

面向产品经理和业务负责人的成果，按[面向人工审核的写作规范](references/review-writing.md)组织为审核摘要、业务正文和追溯附录。先讲本次结论、范围和需要决定的事项，再给依据；技术编号和维护记录按需查阅。初期先还原用户处境与问题，再讨论功能，不让审核人从台账中自行寻找重点。

用户从项目管理目录的固定 `查看与试用.html` 找到同版正文、原型与实际操作记录，具体路径见[项目定位规范](references/workspace-layout.md)。它由工具随记录更新；当前候选与有效版本分别展示。每轮仍直接给出本次修改、一个可执行试用任务和确需人处理的事项。S2—S4 持续追踪同一组真实任务，不要求三类原型使用同一文件或相同界面。

有关键路径走不通、未测或等业务决定时，在当轮给用户的阶段结论和 checkpoint 里写出具体事件、停在哪一步、影响谁、谁接手以及复测条件。已有原文答案的列为待修复，需补真实事实的列给实际责任人。只有关键业务检查均通过且仅余人工授权时，才概括为“待批准”。

新业务项目默认使用中文目录和中文管理文件，具体分区见[项目定位规范](references/workspace-layout.md)；已有英文项目自动识别并在原布局接续。成果为中文 Markdown，原型为 HTML/CSS/JavaScript。流程图等保留可编辑 draw.io 与重要图的 SVG/PNG，执行相应阶段规范。领域资料按[领域扩展契约](references/domain-extension.md)按需读取，不能直接成为企业规则。公共模板入口见[模板索引](assets/templates/index.md)。

现有 meeting-design-to-prd 等方法按需复用，不引入另一套项目状态或目录。工具不可用则记录未执行范围及替代结果，不能声称完成；S5 必用的 `/ecc:plan-prd` 缺失或失败时，依赖它的生成保持未完成，按[命令接入规范](stages/prd-authoring-and-review/references/ecc-plan-prd.md)处理。正式交付准备可复核清单与 manifest，取得对应版本的真实授权后 deliver；从实际包内完成检查并用 delivery-check 登记后，才报告交付验收完成；不自动向外发送。
