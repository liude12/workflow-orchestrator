# 登记可直接阅读和试用的阶段材料

## S2 业务模型与 S3 产品方案

准备同一版本的主文档、原型、实测记录和附件，放在一次审核涉及的工作稿目录中。正文提供两个可以点击的入口，分别通向 HTML 原型与实际操作记录，也可先链接至介绍页，再由介绍页进入。S3 还应链接系统页面布局说明，或在正文一个明确标题下写清整个系统的页面与功能分布。

原始资料、确认依据及需要保留的独立快照按原流程登记。提交 T02/T03 时，在已有的 `put` 数据中加入 `review_bundle`。以下是 S2 的示例字段，换成该项目实际文件与定位。已有字段如 `requirement`、`type`、`title` 和 `refs` 仍按[本地命令](local-tools.md)填写。

```json
{
  "body_file": "本轮工作稿/业务模型说明.md",
  "review_bundle": {
    "root": "本轮工作稿",
    "files": [
      {"role": "prototype", "path": "业务原型/index.html", "locator": "申请与取消演练"},
      {"role": "operations", "path": "业务原型/实际操作.md", "locator": "申请与取消的实际观察"},
      {"role": "support", "path": "业务原型/取消后.jpg", "locator": "实际操作中引用的取消后视图"}
    ]
  }
}
```

`root` 和 `body_file` 可用绝对路径或相对于本次命令工作目录的路径。正文应位于所选根目录内，脚本会自动保存正文。其余文件在 `files` 中逐个列明，路径以该根目录为基准。S3 独立布局文件使用 `role: "layout"`；如果布局写在正文，使用 `review_bundle.layout_heading` 指定有内容的 Markdown 标题文字，例如“全系统初步页面布局”，省略井号。一次审核中引用的图片、样式、数据、图源及其他材料可用 `support`。需要核对附件中的本地引用，包括从验证记录跳回主文档的链接。

工具按原目录层级保存本次明确列出的文件，保留原字节和相对链接。成功后从返回的项目相对 `path` 打开登记版正文，例如 `02-业务建模/业务模型/<ID>/v1/业务模型说明.md`。逐一打开原型、实测记录、布局和必要资源；原型含脚本动态加载、复杂 Markdown／脚本文档或外部服务时，尤其需要实际打开和操作。工具做基础静态链接和文件完整性检查，实测充分性、业务结果和授权范围由对应阶段实际核验。正式交接和导出会再次检查登记版及其审核附件。

旧项目按已有路径读取。普通草稿仍可单独登记。首次为旧记录补齐原型或修正链接时，保留历史内容并按 `expected_version`、`change_reason` 登记新版本；准确说明受影响的文件及复检范围，复用覆盖本次范围的有效决定。原型和记录随同版 T02/T03 保存，`put` 自动计算其哈希并将其登记为可随清单导出的证据。

## S4 原型入口与资源同版登记

P04 正文必须能通过实际阅读链接进入已登记的 HTML。包含命名入口或多个本地文件时，沿用 `review_bundle`：`body_file` 指向说明稿，`root` 选取包含说明与原型的工作稿目录；在 `files` 逐一列出 HTML 入口（`role: "prototype"`）和必要资源（`role: "support"`）。例如正文位于 `说明/P04.md`、入口位于 `原型/index.html`，正文链接写 `../原型/index.html`；HTML 引用的 CSS、脚本、图片及 CSS 中的资源也须列出，不能只登记哈希快照。

工具在写入版本前核对阅读入口、所有识别到的本地引用及 HTML/SVG 锚点，拒绝缺失、未登记、越界和重复路径；成功时保持原相对层级，并自动记录各文件哈希。正文入口由保存路径与同版 evidence 映射，后续门禁、交接和交付重新核对文件及哈希。失败不会形成已登记的半套版本。

单个自包含 HTML 仍可先 `snapshot`，再通过 `evidence.kind: "source"` 登记。此时正文须按**最终登记正文目录**链接工具返回的真实快照路径，不能直接把项目根相对路径贴成正文相对链接；快照引用的本地文件仍须逐一登记并保持相对位置。容易计算错路径时，使用上述 `review_bundle` 保存说明和命名入口。

旧 P04 可以继续读取；若入口或资源缺失，门禁/交付会提示登记新版本补齐，保留旧版本与已有证据。静态检查不执行 JavaScript、不验证外部服务或动态生成的路径，仍须从返回的登记版入口实际打开并操作，记录动态依赖和任务结果。

## S5 的 PRD 与 SRS 同版交付

PRD 作为 T05 正文，SRS 作为同版的规格附件。两份文档在正文中互相提供可点击的阅读入口。将它们及本次引用的必要图片、图表、说明等文件放入同一个工作稿根目录，再以 review_bundle 登记。下面只展示需加入已有 put 请求的字段。

```json
{
  "body_file": "本轮工作稿/产品需求文档.md",
  "review_bundle": {
    "root": "本轮工作稿",
    "files": [
      {"role": "srs", "path": "软件需求规格说明.md", "locator": "与本版 PRD 对应的实现契约与验收"},
      {"role": "support", "path": "附件/状态转换.svg", "locator": "SRS 状态与转换引用图"}
    ]
  }
}
```

一次登记恰好包含一份非空 Markdown SRS。PRD 可直接链接 SRS，也可通过同版说明页进入，SRS 同样应能通过阅读链接返回 PRD。支持文件逐一列明，原始资料和人工回复等独立依据继续使用 evidence。正文中使用文件相对链接，REQ、AC 及其上游关系仍通过 refs 保存。

成功后，从 put 返回的 path 打开 PRD，再查看 SRS 和其引用文件。正式 handoff、resume 对交接的复核及 deliver 会检查已成套登记的 T05。SRS 与支持文件自动进入 evidence，文件哈希和审核材料信息参与 manifest，导出会保留同版路径与字节。两份文档的内容一致性和业务充分性按 S5 质量要求实际核对。

旧的单正文 T05 可以按既有记录读取和接续。新双文档交付采用上述方式。已采用双文档的 T05 后续修改时，继续提交包含两份文档的 review_bundle，并填写 expected_version 与 change_reason。原版本及其附件保留为历史，新版需要重新核对受影响的检查和批准范围。
