# 面向人工审核的写作规范

默认读者是产品经理和业务负责人。让读者先理解业务结论，再决定是否查详细依据。本文规定表达和阅读顺序，不改变成果、证据、版本或授权要求。

## 一份主文档，三层阅读

1. **审核摘要**：通常一屏到一页，先说本次改了什么或建议什么，再给本轮应看的位置或可试任务、真正需要人回复的事项。用具体业务说明范围、理由和重要限制，不逐章缩写全文，也不用待决总表代替本轮阅读任务。
2. **业务正文**：先用一个正常案例说明“谁在什么情况下做什么，会得到什么结果”，再写重要规则、异常和取舍。需求整理解释问题与期望结果，后续方案解释操作和反馈。S5 的 PRD 按用户价值、范围和可验收业务能力组织，配套 SRS 展开研发和测试需要的完整行为规格，并提供对应入口。
3. **追溯附录**：放来源定位、稳定编号及版本关系、原始反馈、逐项检查、工具日志、哈希与交接记录。正文用有含义的链接带过去；关键事实在正文就标明已确认、待核实或建议，不让读者看完附录才知道是否可靠。

首行保留项目名、版本和当前状态即可；不要把长排 ID、检查代码或来源版本放在结论前。三层阅读不另建状态系统或重复审批文档。已有主记录用名称链接引用；摘要与主记录不一致时先纠正，不能让两个版本各自成立。

## 摘要必须回答

| 读者的问题 | 应呈现的内容 |
|---|---|
| 为什么要看？ | 本次问题、阶段结论、相较上次变化；首稿写首次整理 |
| 打算怎么做？ | 一句业务建议及主要依据，做到哪里、暂不做什么 |
| 现在看哪里、试什么？ | 一个主阅读/试用入口、起始角色、关键操作与应看到的结果；没有原型就说明只能核对文字 |
| 哪些还不确定？ | 有来源支持的事实、建议、待核实事实、未执行验证分开说 |
| 我需要决定什么？ | 具体选择和代价；无新增事项写清楚，不泛问是否确认全文 |
| 决定后会怎样？ | 影响的成果/范围、可推进工作和仍需补齐的条件 |

结论给出正文中的依据位置，“详见附件”不能代替解释。审核任务直接写在摘要和当轮回复中，不另造一份必须阅读的摘要文件。内部检查已做什么、哪里失败或未测需如实可见。仅文字修订不涉及业务取舍时说明，不重复要求已有适用批准；教学或格式演练明确本轮无需作真实业务决定。

## 待决事项用决定卡

提问前先区分：可从已有资料取得的答案由 AI 查找并回填；需要补充的企业事实写清所需材料或现场情况；实质业务取舍给选项与影响；AI 能完成的设计、检索或技术核对先执行，不包装成让用户回答的问题。仍缺实际授权或新业务决定时再按真实范围提出。

需要人取舍的事项用业务标题，依次填写；纯事实补充不必凑候选方案：

- **需要决定**：一个明确问题；事实缺失写请核实什么，不伪造成偏好选择。
- **选择与影响**：可行选项分别影响哪些用户、成本、范围或风险；未知代价待估，不编收益。
- **建议与依据**：有依据才推荐；不足时说明缺什么，推荐不等于决定。
- **谁回复 / 何时需要**：实际职责与依赖时点；未知写待指派，不编负责人和期限。
- **本次确认范围**：文档名称、版本、具体条款/范围，以及是否包含阶段继续。交付批准仍绑定具体文件清单。
- **实际答复**：待答复或已有适用回复的链接，不预填同意。可提供“选 A；调整为……；暂缓，待……”的回复方式。

按影响排序，摘要突出本轮确需回答的事项；未到依赖时点的事项说明何时需要，AI 自行处理的工作留在进度与记录中，不一起列作“请您确认”。重要阻塞仍需可见。阅读认可、业务规则决定、阶段继续、交付授权含义不同，应说明本次回复覆盖的实际工作；由 AI 映射到内部记录，不要求用户学习记录分类。已有适用决定直接引用，不从笼统“通过”推断全部授权，也不重复索取已明确提供的授权。

初期补问先完成资料缺口分析，完整问题单随同一轮消息提交，按主题分组并写明已知信息、缺什么、影响和回复方式；摘要突出优先事项不等于把其余已知问题拆到下一轮。条件分支放在同一包，可整段自然语言回复或写暂不清楚。只有新回复或新增材料引入新缺口、冲突时，才针对相关未解决项集中补问；未答保留待核实，不重复整份问卷。

## 用词与版式

- 标题用业务含义，如“误点完成后如何恢复”，不要仅写“R02 状态转换”；编号可跟在名称后或置于附录。
- 将必要术语解释为业务话，如用“满足哪些条件才能操作”代替“守卫条件”。维护索引、闭包、门禁等程序词不进入业务结论。
- 正文保留影响判断的事实、约束、异常、业务关系和必要依据；来源编号、哈希、命令及内部质检细节放在可追溯记录中。不要为了简短删除业务关系，也不要把编写过程的自我证明反复放进正文；对整个文档适用的草稿或验证限制可集中说明，局部重要未知仍在相应位置标注。
- 一段一个观点，仅加粗结论、边界与待决。正文表格通常不超过五列；复杂流程、长证据改用步骤、决定卡或附录。
- 写具体业务，不逐格填“已完成、见前文、待确认”。删除不适用空章节或说明理由，保留基线实质覆盖与映射。
- S2 业务原型入口放在 T02 摘要，S3 功能验证原型入口放在 T03 摘要，S4 打磨原型入口放在 P04/T04 摘要。延续同一真实任务的角色、对象和预期结果，分别说明本阶段验证业务运转、功能承接或打磨体验，不能互相顶替。按实际工作节奏覆盖暂停/返回、持续补录、跨角色接手等适用情境，不机械要求无关场景。
- 每轮只给一个明确的当前阅读/试用主入口；优先使用实际已生成的管理目录 `查看与试用.html`，由工具导航到同版正文及附件，标明阶段用途、候选/有效状态和版本。尚未生成时给可打开的登记版正文或原型，不写不存在的链接。业务结论和试用任务仍在正文摘要，历史快照保留；正式交付从实际包内入口核对，不用项目导航替代。打开条件与模拟边界在入口处说明，临时服务失效时给可恢复的文件入口。内部实操与真人观察分别报告，生成文件不等于验证通过。
- 变更写“原来 → 现在 → 影响”；首稿不虚构比较历史。

## 提交前的读者检查

只读摘要能否找到本次变化、直接开始一项阅读/试用任务，并知道自己是否需要回复什么？抽一个正常案例和一个重要异常，能否说明处理结果、未知部分及依据？是否仍要翻译内部代码或自行拼接多份文件？摘要、原型与详细规格是否同版一致？

AI 代读只能算可读性内部检查，不称为真实产品经理或业务负责人已审核。表达不清先改写；事实或决定缺失保留真实状态，继续不依赖它的工作。
