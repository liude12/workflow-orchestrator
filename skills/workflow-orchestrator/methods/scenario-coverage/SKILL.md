# 场景覆盖与操作证据适配方法

基于 PM Skills `test-scenarios` 的角色、初始条件、操作步骤和可观察结果方法适配；增加本工作流的来源、版本及实测约束。固定上游与许可见[方法来源说明](../provenance.md)。先按[专业方法接入约定](../../references/specialist-methods.md)确定当前阶段与本轮范围。

## 什么时候使用

关键业务包含多角色交接、多对象联动、重要异常或复杂权限时，用本方法准备或独立复核用例；修改已验证行为时检查受影响的回归。简单且已有覆盖的改动只复用适用用例并更新差异，不强制重新生成整套测试计划。

输入包括本轮目标、确切有效 SCN/RULE、适用 FUN/PAGE、任务路径、既有用例/实际记录、原型版本，以及 S5 的 REQ/AC。哪些阶段尚无这些编号，就使用已有场景和规则位置；S2 不强求 FUN/PAGE 或 AC。没有可操作成果也可编写计划，但不能给实测结论。

## 从有效要求形成用例

1. 列本轮要验证的行为、预期及来源位置，先核对版本和适用范围。示例阈值、页面当前表现、竞品做法及生成模型的常识都不能成为业务预期。
2. 为每条任务确定角色/权限、对象及初始状态、代表性输入、资源或权益前值、相关配置与入口。模拟数据注明模拟；需要人工或外部系统承担的步骤说明接续条件，不伪造外部成功。
3. 按实际用户路径写动作与每步应观察到的结果，覆盖触发到最终业务结果及返回/继续。跨角色时沿同一对象交接，不能靠各角色分别演示不同样例证明闭环。
4. 根据规则和影响选适用分支：校验失败、取消、重复、权限/状态拒绝、资源冲突、处理中断和恢复、跨对象部分结果及已确认阈值边界。用选择依据控制组合范围，不机械套全部状态，也不以“无法测试”代替不适用理由。
5. 同时检查用户可见反馈、对象状态、资源/权益和关联记录等必要结果，以及禁止出现的副作用。一个操作可有多个断言；拒绝动作也应核对原有结果是否按规定保持。
6. 将每个用例对应到现有覆盖记录。正向核对本期关键任务是否都有用例，反向核对每项断言是否有依据。发现无依据预期时记具体待决与受阻用例，交对应来源阶段，不补一个猜测结果凑齐覆盖。

可在现有表格或段落中保留：用例/任务、来源与版本、角色和前提、数据、操作、预期与断言、实际结果、证据、问题与复验。已有字段足够时不新建文件；数量和时长均依据本项目，不沿用上游示例数值。

## 未知与冲突如何处理

规则冲突保留两处来源、受影响行为与决定责任，不能择取最方便实现的一条。受阻用例标为待决定；不依赖该缺口的用例可继续。已确定“待决定时保持状态”之类保护行为可以另测，但这不能证明未知业务规则已经得到验证。

S2 的规则/状态问题回业务建模，S3 的功能路径问题回产品方案，S4 的呈现和交互问题回原型实现；S5 新发现的实质问题也先修上游，再更新文字与对应验收。

## 计划与实际执行分别记录

- **用例计划**：写了角色、步骤、预期和来源，尚无操作观察。状态为未执行，不能直接登记通过。
- **模型推演**：按材料推算结果，标明是推演；不能充作真实浏览器操作、真人反馈或生产系统验收。
- **实际执行**：从本轮登记版或明确测试副本入口操作，记录实际环境、版本、输入、动作、观察及可定位证据，比较每项必要断言；失败保留原记录，修复后记录受影响用例的复验。

已有同版适用证据可复用，注明覆盖范围和差异；不能复用失效结果，不能因为页面能点击或日志写“成功”就判业务通过。原型实测使用本机实际可用的浏览器能力；只在确需重复执行的稳定路径上采用自动化，工具就绪以可观察界面状态判断，不要求额外安装特定框架。

观察不到的结果注明缺口及需要何种证据；页面、源码、截图或测试脚本文件本身都不能证明操作已发生。真实用户验证仍须目标用户的实际任务观察，业务批准由实际有权人给出。
